## 레이어 규칙

```
Manager (순수 로직)  <->  Management (화면 조종)      서로 호출 가능
        ^ 직접 호출 금지          ^ 직접 호출 금지
Window / Panel / Component --> Helper (정적, 읽기 전용) 만
```

- 하위 UI 는 Manager 를 직접 안 본다. 데이터는 Helper 경유, 올릴 건 `event`.
- 패널은 형제 패널의 `RectTransform` 을 고치지 않는다. 자기 구획만 바꾸고 남는 높이는 부모 레이아웃이 나눈다 (원본의 flex).
- 월드 오브젝트는 UI 어휘(`Window`/`Popup`/`Panel`/`View`) 대신 `~Visual` 접미를 쓴다.
- 어셈블리 분리를 권장한다. 순수 계산 어셈블리가 `UnityEngine` 을 참조하지 않으면 `Mathf`(float) 와 `Random` 직접 호출을 컴파일러가 막는다.

## 「스탯이 안 물려 있다」 — 가장 많고 가장 안 보인다

예시 (필드명·수치는 프로젝트마다 다르다):

```js
// 원본
dmg: (cs.gunDmg || cs.dmgEff)                    // 1944.45
dmg: cs.dmgEff * (cs.sideDmgMult || 0.6)         // 31.07
dmg: (cs.laserDps || cs.dmgEff*2) * dt           // 103.58/s
```
```csharp
// 유니티 (틀림) — 기준값이 빠지고 배수만 남았다
AddShot(..., ShotColor);            // damage 기본값 1f  (1/1944)
Damage(target, 2f * dt);            // x2 만 남음        (1/52)
```

증상: 적 HP 는 배수(×361)를 먹는데 피해가 1이라 적이 쌓이고, 엘리트가 살아 적 탄막이 생겨 다른 그림이 된다.
발생 지점: Management 가 Panel 에 주입하는 스냅샷 구조체에서 필드가 빠질 때다. 새 기능을 붙일 때 여기부터 본다.
점검법: 원본에서 계산 결과(`cs.` / `s.`)가 들어가는 자리를 전수 나열하고 유니티 호출부에 도달하는지 짝짓는다. 남은 리터럴 상수가 원인이다.

### 스냅샷 구조체는 「안 쓰는 필드가 있으면 계약이 틀린 것」

UI 로 넘기는 `XxxEntry` 의 모든 필드는 화면 어딘가에 도달해야 한다. 표시 쪽이 안 읽는 필드는 누락 신호다.
사례: 선택 카드 엔트리의 `Effects`·`FusionDescription` 이 선언만 되고 안 채워진 채 몇 달 남았다.

## 「원본에 없는 상한」

원본에 있는 상한만 옮긴다. 성능 걱정으로 넣은 캡은 원본 밀도를 깎는다. 예시 (값은 원본에서 다시 잰다):

| 대상 | 원본 | 잘못 넣은 값 | 결과 |
|---|---|---|---|
| 발사체 | 상한 없음 (정상 상태 ~110) | `MaxShots = 40` | 40발에서 발사가 멎는다 |
| 폭발 파편 | 상한 없음 (실측 161) | `MaxParts = 90` | 격파가 겹치면 폭발이 안 터진다 |
| 적 | `> 60` 이면 안 낳는다 | 60 | 맞다 |

뷰 폭주 방어가 필요하면 정상 상태의 2배 이상 여유값으로 두고 주석에 실측치를 남긴다.

## 「거동이 빠졌다」 — 배치는 맞는데 안 움직인다

원본 함수 인자에 `t` 나 `dt` 가 있으면 움직이는 것이다.

| 대상 | 원본 | 빠진 것 |
|---|---|---|
| 발사체 | 발사 때 잡은 `s.target` 으로 매 프레임 선회 (`clamp(9*dt,0,1)`) | 유도 전체. 직진해서 빗나갔다 |
| 호위 드론 | 0.5초마다 최근접 적에게 발사 | 사격 코드 자체. 궤도만 돌았다 |
| 배경 장식 프롭 | 대부분 `t` 로 애니메이션 | 연출 전체. 정적 PNG 였다 |

주의: 일부러 유도가 없는 것도 있다. 보조 무기는 `target:null` 이라 직진, 전용 대형 무기는 별도 리스트라 유도 없음. 전부 유도로 통일하면 오답이다.

### 「비슷한 유도」로 뭉개기 쉬운 6가지

유도체를 `Vector2.Lerp(v, desired, dt*k)` 한 줄로 옮기면 비행 모양이 달라진다.

| # | 원본 | 뭉갠 구현 | 보이는 차이 |
|---|---|---|---|
| 1 | 발사 때 잡은 `m.tgt` 유지, 죽었을 때만 재획득 | 매 프레임 최근접 재조준 | 궤적이 꺾이고 여러 발이 한 적으로 몰린다 |
| 2 | 각도 선회 (`na = cur + d2`) | 속도 벡터 Lerp | 속력도 줄어 곡선이 무뎌진다 |
| 3 | 선회 예산 `turned ≤ π`, 다 쓰면 직진 | 없음 | 빗나가면 영원히 빙빙 돈다 |
| 4 | 뒤쪽(`\|d2\| ≥ 2.7`) 표적은 선회 안 함 | 없음 | 뒤로 급선회 U턴 |
| 5 | 가속 `min(300, sp + 360·dt)` (직진 시 260) | 속력 고정 | 원본은 150에서 300까지 붙는다 |
| 6 | 개체별 선회율 `5·(0.8+rand·0.4)` · 조준 오프셋 `±20` · 흔들림 | 전부 고정값 | 미사일이 한 덩어리로 겹친다 |

- 꼬리(trail): 원본은 최근 8점 폴리라인이다. 선분 뷰도 풀에서 빌리고 본체가 사라질 때 같이 반납한다.
- 수명 종료: 원본 미사일은 수명이 다해도 그 자리에서 폭발하고 splash 를 준다. 조용히 사라지면 광역 피해가 빠진다.

## 메인 루프의 게이트 조건을 한 줄씩 옮긴다

함수 단위로 이식하면 루프의 `if` 조건이 사라진다.

```js
// 원본.html — 메인 루프 본체 (인용할 때 라인 번호를 grep 으로 재확정한다)
if(screen==='combat'){
  drawScene(t,dt);                                   // 그리기는 항상 돈다
  if(!(AUG&&AUG.open) && !(G&&G.paused)){            // 시뮬 게이트
    updateCombat(dt);
    …
  }
}
```

사례: 「선택 모달이 뜨면 시뮬 정지」 한 줄을 빠뜨려 카드를 고르는 사이 격침당했다.

- 원본 루프 본문을 줄 단위 표로 만들고 각 조건을 유니티 쪽과 짝짓는다.
- 그리기 계속·시뮬만 정지인지, 둘 다 정지인지 구분한다. 대개 그리기는 계속이다.
- 정지 게이트(모달 · 일시정지 · 결과 · 컷신)를 전부 나열한다.
- 가변 dt 는 원본과 같은 상한으로 클램프한다 (예: 0.033, 원본 실측값).

검증: 모달을 띄운 채 수백 프레임을 흘리고 `시각·개체 수·HP` 가 고정인지 본다.

```
778프레임 경과 · ctx.Time 3.952 고정 · 적 83기 고정 · HP 403.0 고정   통과
```

이 상태가 가장 안정적인 캡처·측정 프레임이다 (공통절차 「교전 중 프레임을 얼려서 본다」).

## 원본의 배열 순회 방향은 사양이다

배열을 훑으며 제자리에서 고치는 로직(낙하·전파·연쇄·정렬·확산)은 순회 방향이 결과를 바꾼다. 이유: 방금 고친 칸을 같은 순회에서 다시 본다.

| 원본이 훑는 방향 | 한 번의 호출에서 일어나는 일 |
|---|---|
| 오름차순, 「다음 칸이 비었으면 옮긴다」 | 하나가 빈 자리 끝까지 미끄러지고 중간은 비어 남는다 |
| 내림차순, 같은 일 | 각각 한 칸씩만 움직인다 |
| 한 번에 모아 압축 | 줄 전체가 한 번에 정렬된다 |

몇 프레임 뒤 화면은 비슷해서 차이는 중간 프레임과 연쇄 타이밍에서만 드러난다.
사례: 위→아래로 훑어 내리는 원본에서 세로 빈 칸 3개에 말 하나가 세 칸을 미끄러지고 중간 두 칸이 비었다. 「열 압축」이면 다른 보드였다.

- 루프 방향과 인덱스 산술을 그대로 옮긴다. 같은 결과가 아니라 같은 절차다.
- 모아서 처리하지 않는다. 중간 상태가 사양이다.
- 빈 자리를 연속으로 만든 입력과 떨어뜨려 만든 입력, 두 벡터를 정답지로 남긴다. 세 방향이 서로 다른 값을 내므로 방향이 고정된다.

```bash
# 원본에서 제자리 수정 루프를 찾는다 — 방향을 눈으로 확인한다
grep -nE "for *\(.*(i\+\+|i--|--i|\+\+i)" 원본.js
```

## 먼저 처리한 것이 뒤 판정을 막는다

한 루프에서 판정 여러 개가 즉시 자료를 고치면 앞 판정이 지운 자리를 뒤 판정이 못 본다. 순서가 곧 결과다. 전형은 이미 처리된 자리를 거르는 가드다.

```js
// 예시: 첫 칸이 이미 비었으면 건너뛴다 — 앞 판정이 비운 자리다
const isBlank = cells[i] === "";
if (group.every(x => cells[x] === decided && !isBlank)) { … 제거 … }
```

| 겹치는 입력 | 순서를 지키면 | 「잘 만든」 판정이면 |
|---|---|---|
| 큰 패턴과 작은 패턴이 한 칸 공유 | 큰 쪽만 점수 | 둘 다 점수 |
| 판정 길이보다 긴 연속 | 앞부분만 먹고 꼬리가 남는다 | 전부 먹는다 |

사례: 가로 4연속·세로 3연속 공유 판에서 4점만 나고 세로 두 칸이 남았다(교과서 판정이면 7점). 5연속도 4점만 났다.

- 판정 순서를 원본 호출 순서 그대로 옮긴다. 묶어서 판정하지 않는다.
- 즉시 수정을 「전부 찾고 한꺼번에 제거」로 미루지 않는다.
- 앞 판정이 남긴 가드 조건(빈 자리·처리 완료 표시)을 빠뜨리지 않는다.
- 겹치는 입력을 벡터로 남긴다. 안 겹치는 입력으로는 안 잡힌다.

## 조기 반환 가드는 뒤따르는 로직보다 넓어야 한다

빠른 탈출이 판정보다 좁으면 일부 입력만 조용히 건너뛰고, 데이터 탓으로 넘어간다.

```csharp
// 틀림 — 정규식은 "/ Lv" 처럼 공백이 낀 것도 잡는데 가드가 "/Lv" 만 본다
if (text.IndexOf("/Lv") < 0) return text;
return LevelScaleRegex.Replace(text, …);
```

가드는 판정식의 가장 느슨한 부분집합으로 잡는다 (위 예는 `"Lv"`). 가드에 걸리는 케이스와 안 걸리는 케이스를 하나씩 실측한다.

## 충돌 · 크기를 상수로 박지 않는다

```js
if(dx*dx+dy*dy < (e.r + s.r + 2)**2)   // 원본 — 양쪽 반지름을 다 본다
```
```csharp
HitTest(s.Position, 10f);              // 틀림 — 탄 반지름을 안 본다
```

원본이 개체에 실어 보내는 반지름(`shots[].r`)을 그대로 통과시키고 창 배율을 곱한다 (상대편 반지름은 이미 스케일된 값).
탄 반지름은 종류(주무기 · 보조 · 요격 · 전용 · 드론)마다 다르다. 사례: 눈대중 상수로 특수탄이 2~3배 작았다.

## 회전은 여러 번 겹쳐 걸린다

```js
drawEnemy:       ctx.rotate(e.angle)      // e.angle = π/2 (스폰 시)
drawEnemySprite: ctx.rotate(Math.PI/2)    // 스프라이트 '위' -> +x 정렬
// 합 = π -> 앞머리가 화면 아래(플레이어)를 본다
```

| 대상 | 원본 회전 | 틀렸을 때 |
|---|---|---|
| 적 | `e.angle + π/2` = 180° | 등을 보이고 내려온다 |
| 호위 드론 | `atan2(ownerY−dr.y, ownerX−dr.x) + π` (주체 바깥) | 전부 오른쪽만 봐 커서 아이콘처럼 보인다 |

점검법: 그 draw 트리의 `rotate(` 를 전부 찾아 합산한다.
스프라이트 향하는 축은 프로젝트에서 하나로 통일한다. `+x` 로 구웠으면 회전은 `atan2(vy,vx)` 그대로이고, 한 뷰만 `−90°` 를 붙이면 한쪽이 틀어진다.

## 수치 계층

- 계산은 `double` 이다 (원본 JS 숫자는 전부 double). float 상대오차 실측 1.3e-7 (`gunDmg` 1944.4539975 → 1944.45374) 은 정답지 1e-9 판정을 못 넘는다.
- 확률은 주입식 RNG 만 쓴다. 기본 난수를 직접 부르지 않는다. 이유: 재현 불가 = 채점 불가.
- 물리 엔진을 섞지 않고 판정은 자체 코드로 한다. 원본이 물리 엔진 위에서 돌면 반대다 (아래).

#### 원본이 물리 엔진을 쓰면 규칙이 뒤집힌다

혼입 금지는 원본에 없는 거동이 생기는 것을 막기 위해서다. 원본이 물리 엔진(Box2D 계열이 흔하다) 위에서 돌면 엔진을 안 쓰는 쪽이 원본에서 멀어진다.
물리 상수·스텝 순서를 캐는 법은 `공통절차.md` 「런타임에서 직접 캐내는 법」이 정본이다.

| 먼저 확인한다 | 어떻게 |
|---|---|
| 원본이 물리 엔진을 쓰나 | 런타임 인스턴스의 거동/컴포넌트 목록을 뒤진다 (`공통절차`·PD 「런타임을 먼저 찔러라」). 쓰면 반발·마찰·밀도·감쇠·충돌 도형·월드 중력을 재지 말고 읽는다 |
| 엔진 계열이 같은가 | 같으면 파라미터가 1:1 로 매핑된다 |

같은 계열이면 실측 파라미터로 엔진을 쓰는 것이 재구현보다 가깝다. 단 셋을 지킨다.

1. 엔진 스케일을 원본과 맞춘다. 내부 상수(접촉 슬롭 · 반발이 죽는 속도 임계)가 절대 크기에 의존하므로, 원본의 「1 미터 = N 픽셀」을 따라야 같은 지점에서 안 튄다. 어긋나면 다중 충돌 뒤 안정화가 갈리고 단발 궤적 검사로는 안 잡힌다.
2. 채점을 실제 경로에서 한다. 헤드리스 계산으로 채점할 수 없으니 재생 모드 검사로 옮긴다 (`공통절차` · 에디터 다리 `PLAYMODE=1 Tools/unity-batch.sh`).
3. 파라미터를 맞추지 말고 읽는다. 정답지가 통과하도록 반발·마찰을 고르면 없는 실측을 지어내는 것이다.

주의: 접선(마찰) 거동은 계수 하나로 재현되지 않는다. 회전 관성이 붙으면 접선 속도비가 흩어지고 각속도 부호까지 바뀐다. 원본이 회전 강체면 「반사 벡터로 튕기는 점」 모델로는 원리적으로 못 낸다.

## 밸런싱은 범위를 물어 채록하고, 규칙은 채록 밖에서 검증한다

레벨이 있는 게임의 가장 흔한 미완성은 1레벨만 맞추는 것이다. 「원본보다 쉽다/어렵다」는 정적 캡처에 안 잡힌다.
전수는 비용이 폭발하고 1개로는 규칙이 안 나오므로 범위를 확정표(11-b)로 못 박는다.

| 단계 | 무엇을 |
|---|---|
| ① 묻는다 | 「앞 몇 개 레벨까지 원본과 똑같이 맞출까요?」 — PD 가 착수 질문에서 받는다 |
| ② 채록 | 그 범위를 전부 원본에서 실측한다. 「대표 몇 개」로 줄이지 않는다 |
| ③ 규칙 도출 | 채록값에서 공식·표를 뽑는다 |
| ④ 채록 밖 검증 | 도출에 안 쓴 레벨로 공식을 검산한다 (홀드아웃) |

### ④가 없으면 규칙이 아니라 암기다

채록 N개에 맞는 공식은 언제나 만들 수 있다. 채록에 안 쓴 레벨에서 맞아야 규칙이다. 채록 개수를 정할 때 검증용 몫을 떼어 둔다.

주의: 홀드아웃을 통과해도 등급은 ②(실측)까지다. 「고정 간격 + 가중치 뽑기」와 「위협 예산」이 같은 스폰 곡선을 냈다. ①로 올리는 것은 소스 직독 · 함수 후킹 · 죽일 조건을 건 가설 시험뿐이다 (PD 「근거 등급」 · 재발방지 `#128`).

### 자유 피팅은 「데이터마다 다르다」로 오독시킨다

파라미터를 다 풀고 레벨마다 맞추면 값이 레벨마다 달라져 레벨표에 N벌을 적는 틀린 결론이 난다.
사례: 발사점 보정 진폭이 레벨마다 달랐는데, 절편을 아는 값으로 고정하자 전 레벨이 한 값(잔차 0.07 이내)이었다. 원인은 모델 범위 밖 표본 한 점이었다.

자유도를 먼저 줄이고 맞춘다. 실측으로 아는 항은 고정한다.

### 「난이도가 같다」는 배치가 아니라 성공 범위로 잰다

재는 값은 그 레벨을 깨는 입력의 범위다.

| 하지 않는다 | 한다 |
|---|---|
| 배치·좌표 일치율 | 입력을 격자로 훑어 성공/실패를 원본과 격자점마다 대조 |
| 「깨진다/안 깨진다」 | 깨지는 입력 구간의 시작과 끝 |
| 한 번 깨봤다 | 격자점마다 n 회, 원본이 갈리는지도 본다 |

주의: 성공 범위를 비율로 비교하지 않는다. 우리 구간 개수가 분모를 바꾼다. 축은 갈린 격자점 수다.

## 원본이 스스로도 재현하지 못하는 구간이 있다

「같은 입력이면 원본이 같은 답을 낸다」는 전제가 깨지는 구간이 있다. 웹 원본의 들쭉날쭉한 프레임 간격이 스침·저속 정착·다중 접촉에서 증폭된다.
사례: 발사 위치가 0.001 px 이내로 같은 두 발이 다섯 번째 모서리 접촉에서 33 ms 어긋나 한쪽만 골인했다.

| 무엇 | 어떻게 |
|---|---|
| 판정 | 같은 입력을 n 회(≥3) 돌려 갈리는지 본다. 2회로는 부족하다 |
| 분류 | 갈리는 벡터는 지우지 않고 「비결정」으로 분류한다 |
| 채점 | 불일치로 세지 않되 「비결정 N건 제외」를 리포트에 반드시 찍는다 |
| 정답지 고르기 | 접촉이 적고 짧게 결판나는 샷으로 고른다 |

### 이것을 면죄부로 쓰면 그 순간 규칙이 무너진다

- 원본이 갈린다는 것부터 재서 확증한다. 안 맞는 자리를 보고 추측하지 않는다.
- 갈리는 빈도를 잰다. 원본 10회 중 9회 성공인데 우리가 0회면 우리 결함이다.
- 제외 범위를 넓히는 것은 점수를 근거로 값을 고르는 것이다 (`재발방지` 참조).
- 제외 건수는 항상 따로 보고한다.

### 정답지 — 수치 환원을 증명하는 유일한 수단

원본을 N가지 상태로 돌려 계산 결과 전 필드를 덤프한 것이다. 없으면 공통절차 「A/B 측정」의 A/B 개체 수 판정으로 대체한다.

#### ⓪ 이건 프로젝트가 직접 만드는 것이다 — 어디서 받아오는 게 아니다

| 무엇 | 누가 | 언제 |
|---|---|---|
| 원본을 헤드리스 브라우저로 돌려 정답지(json) 덤프 | Transfer_Programmer (Client 지식 기반) | G2 를 열기 전 |
| 파서 · 필드 대응 · 채점기 · 에디터 메뉴 (`.cs`) | Transfer_Programmer | 같이 |
| 어느 상태를 몇 개 뽑을지 (스위트 설계) | Client 지식이 `02_시스템_*.md` 로 넘긴다 | 학습 단계 |

- 하네스 제작은 「스탯 환원」 아래 묻지 말고 별도 리스트업 항목으로 올린다 (PD 「재는 도구를 먼저 만든다」).
- 하네스가 없는 동안 그 수치 항목은 `미측정(③ 하네스 없음)`, 달성률 0% 다 (분석로직 「섹션별 기입 규칙」).
- 전제: 정답지는 임의 키 수백 개짜리 맵이라 `JsonUtility` 로 못 읽는다. 선택지와 접점 격리는 [DataFramework 「전제」](DataFramework.md).

| 자리 | 무엇 | 수명 |
|---|---|---|
| 정답지 JSON | N벡터 | 프로젝트와 함께 남는다 |
| 채점기 (에디터 메뉴) | 정답지를 읽어 이식본과 대조 | 게임별 하네스라 이관이 끝날 때까지 남긴다. 회차용 검사기만 회차 끝에 지우고 `Tools/Verify/out/` 은 회차마다 비운다 |

주의: 채점기 없이 정답지만 남은 상태는 「검증됨」이 아니다. 스탯 계통을 다시 손대면 채점기를 먼저 복원해 돌린 뒤 고친다.

#### ⓐ 순서를 지킨다 — 출처 대조가 채점보다 먼저다

정답지는 특정 시점의 원본 데이터를 전제로 뽑혔다. 전제가 깨지면 실패가 전부 계산 오류로 보인다.
출처 대조기를 먼저 돌려 계열별 노드 수가 정답지 메타와 같고 주입 키·유닛 코드가 전부 있는지 본다. 「전부 일치」여야 그다음 실패를 계산 오류로 읽는다.

#### ⓑ 이름 대응은 규칙 두 개 + 예외표로 끝난다

원본 JS 는 camelCase, 이식본은 PascalCase 다. 예: 310키 중 296키가 규칙만으로, 13건이 `_xxxDed → XxxDedicated` 규칙으로 맞았다.
예외가 많으면 대응표가 아니라 이식을 의심한다.
대응 필드가 없으면 건너뛰지 않고 「대응 필드 없음」으로 세어 보고한다. 사례: 원본 `s.guidedMult`(2948)를 `GuidedMul` 하나에 겸해 쓰던 미이식을 잡았다.

#### ⓒ 실패를 세 갈래로 갈라 놓고 시작한다

채점기가 상대오차 분포를 같이 찍는다.

| 갈래 | 신호 | 처방 |
|---|---|---|
| 자료형 한계 | 상대오차 1e-9 ~ 1e-6 구간에 몰림 | float → double. 계산은 안 건드린다 |
| 진짜 계산 차이 | 1e-6 초과 · 특정 스위트/필드에 집중 | 원본 라인과 대조 |
| 정답지 쪽 결함 | 기대값이 모든 벡터에서 같은 이상값 | 비교에서 빼고 왜 뺐는지 적는다 |

예: 79,897필드 중 완전일치 77.7% · 1e-9~1e-6 구간 12,748 · 1e-6 초과 754. 분포 없이는 754건을 못 찾는다.

#### ⓓ 정답지도 틀린다 — 「기대값이 전 벡터 동일」이면 생성기를 의심한다

예: `stats._syn` 이 230벡터 전부 `{}` 였다. 원본이 `s._syn = new Set()` 이고 `JSON.stringify(new Set([...]))` 는 언제나 `{}` 다. 6종을 옳게 켠 이식본이 71건의 가짜 실패로 찍혔다.
생성기가 `Array.from()` 으로 다시 뽑기 전까지 측정 불가 필드로 빼고 코드에 적는다.
정답지를 뽑을 때 JSON 을 못 건너오는 `Set` / `Map` / 함수 / `undefined` / `NaN` / `Infinity` 를 먼저 훑는다.

#### ⓔ 입력에 안 적힌 암묵 상태를 같이 옮긴다

정답지 입력에는 원본이 로드 때 채우는 기본값이 없다. 비어 보이는 보유 목록에도 기본 지급분이 들어간다 (`if(!owned.default) owned.default = 1` 류가 `boot()` 근처에 있다). 빠지면 보유 보너스 계열 벡터가 전멸한다.
규칙을 하네스에 베끼지 말고, 상태 주입 뒤 로드 완료 이벤트를 한 번 더 쏴 이식본의 기본값 채우기를 다시 태운다. 그 규칙도 같이 검증된다.

#### ⓕ 하네스는 사용자 세이브를 건드릴 수 없어야 한다

조심하는 대신 경로를 없앤다.

- 상태 주입은 파일을 읽지도 쓰지도 않는 전용 API 로만 한다. 예: `SaveManager.InjectVolatile` 이 저장 가능 플래그(`SaveReady`)를 꺼 이후 저장을 무효화한다 (이름은 프로젝트가 정한다).
- 세이브를 만지는 하네스는 `GameInitialize` 가 세운 데이터·매니저를 쓰고 재생 중에만 돈다 (Play → 인트로에서 게임 시작 → 로딩 완료 뒤 · 에디터 다리 `PLAYMODE=1 Tools/unity-batch.sh`). 중복 기동 경로(`DataManager.InitializeFromJson` 직접 호출·`GameManager` 자체 생성)를 두지 않는다. 세이브와 무관한 헤드리스 데이터 검증은 DataFramework 「DataManager」의 `InitializeFromJson` 을 쓴다.
- 에디트 모드에서 `GameManager.Instance` 를 억지로 만들면 남은 `MonoSingleton._isDestroyed` 에 걸려 영구 null 이 된다. 위 방식이면 사라진다.
- 재생 중 가드는 메뉴가 아니라 상태를 만지는 함수에 건다 (예: `GoldenHarness.RequirePlayMode`). 메뉴 가드는 우회된다.
- 파일이 무사한 건 `SaveReady` 차단 덕이다. 메모리 상태는 갈아엎히므로 채점한 세션은 버리고 Play 를 다시 켠다.

### 미리보기 계산은 「실제로 적용했다가 되돌린다」

원본이 그렇게 한다. 예: 「이 강화를 받으면 뭐가 바뀌나」 표는 실제로 획득시켜 스탯을 두 번 계산한다.

```js
const A=computeStats();
AUG.act.add(k); AUG.stk[k]=stk+1;     // 받은 상태로 만든다
const B=computeStats();
AUG.stk[k]=stk; if(!wasAct) AUG.act.delete(k);   // 원복
```

- 원복을 빠뜨리면 실제 스탯이 오염된다. 조기 `return` 경로에서도 원복되는지 본다.
- 캐시가 있으면 두 계산 사이와 끝난 뒤에 무효화한다.

## 데이터 접근

- 자동 생성 파일은 직접 고치지 않는다. 원본(엑셀)이나 제너레이터를 고친다.
- 콘크리트 컨테이너를 만들거나 지우면 `ContainerRegister` 와 `GameRoot` 프로퍼티를 손으로 맞춘다 (DataFramework 「폴더 · 파이프라인」).
- `Id` 가 아닌 컬럼 조회는 컨테이너가 자료구조를 만든다 (로드마다 새로 만들고 행마다 채우는 훅). 로컬 캐시를 따로 들지 않는다.
- 테이블을 추가했으면 조회 성공을 실측한다 (「스탯이 안 물려 있다」).
