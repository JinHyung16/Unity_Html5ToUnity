# 클라 파트 — HTML5 → Unity 이관

상위: [PD](PD.md) (PD)

**담당** — 시뮬 루프 · 계산 이식 · 배선 · 레이어 규칙 · 수치 정밀도 · 데이터 접근.
**한 줄 원칙** — 원본은 **행동할 때마다 계산 결과를 실어 보낸다.** 그 배선이 빠지면 계수만 상수로 남는다.

**역할** — 나는 **지식 담당자**다. 이관에 직접 참여하지 않는다.
[Transfer_Programmer](Transfer_Programmer.md) 가 100% 이관할 수 있도록 **정확한 정보를 제공**하는 것이 산출물이다.
**HTML5 를 실제로 돌려 보며 파악한다** — 정적 코드 읽기로는 순서·타이밍·게이트 조건이 안 잡힌다.

**역할 선언** — 이 역할로 들어갈 때 다음을 **출력한다** (PD 「역할 기동 규약」).

```
[역할 전환] 지금부터 나는 Client(지식 담당)다.
  할 수 있는 것 : 원본 읽기·실행 · 01_게임플로우.md / 99_원본지도.md 작성
  하지 않는 것  : Unity 코드·프리팹 수정 (그건 Transfer_Programmer 가 한다)
```

**이전 역할의 결론은 md 에 적힌 것만 인정한다.** 기억으로 이어가지 않는다.

## 레이어 규칙

```
Manager (순수 로직)  ←→  Management (화면 조종)      ← 서로 호출 가능
        ↑ 직접 호출 금지          ↑ 직접 호출 금지
Window / Panel / Component ──→ Helper (정적, 읽기 전용) 만
```

- 하위 UI는 Manager를 직접 안 본다. 데이터는 Helper 경유, 올릴 건 `event`.
- 패널이 형제 패널의 `RectTransform` 을 직접 고치지 않는다. 자기 구획만 바꾸고
  남는 높이는 부모 레이아웃이 나눈다 (원본이 flex로 하는 일).
- 월드 오브젝트는 UI 어휘(`Window`/`Popup`/`Panel`/`View`)를 쓰지 않는다 — `~Visual` 접미.
- **어셈블리 분리를 권장한다.** 순수 계산 어셈블리를 `UnityEngine` 미참조로 두면
  `Mathf`(float) 오염과 `Random` 직접 호출을 **컴파일러가 막는다.**

## ★ 「스탯이 안 물려 있다」 — 가장 많고 가장 안 보인다

**[예시]** 한 원본의 실측 — 필드명·수치는 프로젝트마다 다르다:

```js
// 원본
dmg: (cs.gunDmg || cs.dmgEff)                    // 1944.45
dmg: cs.dmgEff * (cs.sideDmgMult || 0.6)         // 31.07
dmg: (cs.laserDps || cs.dmgEff*2) * dt           // 103.58/s
```
```csharp
// 유니티 (틀림) — 기준값이 통째로 빠지고 배수만 남았다
AddShot(..., ShotColor);            // damage 기본값 1f  ← 1/1944
Damage(target, 2f * dt);            // ×2 만 남음        ← 1/52
```

**증상**: 적 HP는 배수(×361)를 제대로 먹는데 피해가 1이라 적이 안 죽고 쌓인다
→ 엘리트가 살아남아 적 탄막이 생기고 → 원본과 완전히 다른 그림이 된다.

**발생 지점이 정해져 있다.** Management가 스냅샷 구조체를 만들어 Panel에 주입하는 구조라면,
**그 구조체에 필드가 빠지는 순간 이 결함이 된다.** 새 기능을 붙일 때 여기부터 본다.

**점검법**: 원본에서 계산 결과(`cs.` / `s.`)가 들어가는 자리를 **전수 나열**하고,
유니티 대응 호출부에 그 값이 실제로 도달하는지 짝지어 본다. 리터럴 상수가 남아 있으면 그게 범인이다.

### 스냅샷 구조체는 「안 쓰는 필드가 있으면 계약이 틀린 것」

UI로 넘기는 `XxxEntry` 구조체는 **모든 필드가 화면 어딘가에 도달해야 한다.**
채워 넣기만 하고 표시 쪽에서 안 읽는 필드가 있으면, 그건 여유가 아니라 **누락 신호**다.

> **[사고]** 선택 카드 엔트리에 `Effects`·`FusionDescription` 필드가 **선언만 되고 아무도 안 채웠다.**
> 컴파일도 통과하고 화면도 그럴듯해서 몇 달 남아 있었다.

## 「원본에 없는 상한」

성능이 걱정돼서 넣은 캡이 원본 밀도를 깎는다. **원본에 있는 상한만 옮긴다.**
**[예시]** 한 프로젝트의 실측 — 값은 원본에서 다시 잰다:

| 대상 | 원본 | 잘못 넣은 값 | 결과 |
|---|---|---|---|
| 발사체 | **상한 없음** (정상 상태 ~110) | `MaxShots = 40` | 40발에서 발사가 아예 멎는다 |
| 폭발 파편 | **상한 없음** (실측 161) | `MaxParts = 90` | 격파가 겹치면 폭발이 안 터진다 |
| 적 | `> 60` 이면 안 낳는다 | 60 | ✓ 맞다 |

**규칙**: 원본에 상한이 없으면 게이트를 두지 않는다. 뷰 폭주 방어가 필요하면
정상 상태의 **2배 이상** 여유값으로 두고 주석에 실측치를 남긴다.

## 「거동이 빠졌다」 — 배치는 맞는데 안 움직인다

**원본 함수의 인자에 `t` 나 `dt` 가 있으면 반드시 움직이는 것이다.**

| 대상 | 원본 | 빠진 것 |
|---|---|---|
| 발사체 | 발사 때 잡은 `s.target` 으로 매 프레임 선회 (`clamp(9*dt,0,1)`) | **유도 전체.** 직진해서 빗나갔다 |
| 호위 드론 | 0.5초마다 최근접 적에게 발사 | **사격 코드 자체가 없었다.** 궤도만 돌았다 |
| 배경 장식 프롭 | 대부분이 `t` 로 애니메이션 | **연출 전체.** 정적 PNG였다 |

**부분 유도에 주의.** 원본이 일부러 유도를 안 거는 것도 있다 —
보조 무기는 `target:null` 이라 직진이 정답이고, 전용 대형 무기는 **별도 리스트**라 유도 자체가 없다.
전부 유도로 통일하면 그것도 오답이다.

### 「비슷한 유도」로 뭉개기 쉬운 6가지

유도체를 `Vector2.Lerp(v, desired, dt*k)` 한 줄로 옮기면 **날아가는 모양이 통째로 달라진다.**

| # | 원본 | 뭉갠 구현 | 눈에 보이는 차이 |
|---|---|---|---|
| 1 | 발사 때 잡은 `m.tgt` 를 **유지**하고 죽었을 때만 재획득 | 매 프레임 최근접 재조준 | 궤적이 홱홱 꺾이고 여러 발이 한 적으로 몰린다 |
| 2 | **각도**를 선회 (`na = cur + d2`) | 속도 **벡터** Lerp | Lerp는 속력도 같이 줄어 곡선이 무뎌진다 |
| 3 | **선회 예산** `turned ≤ π` — 다 쓰면 직진 | 없음 | 빗나가면 스쳐 지나가야 하는데 영원히 빙빙 돈다 |
| 4 | 뒤쪽(`\|d2\| ≥ 2.7`) 표적은 **선회 안 함** | 없음 | 뒤로 급선회하는 부자연스러운 U턴 |
| 5 | **가속** `min(300, sp + 360·dt)` (직진 시 260) | 속력 고정 | 원본은 150에서 300까지 붙는다 |
| 6 | 개체별 선회율 `5·(0.8+rand·0.4)` · 조준 오프셋 `±20` · 흔들림 | 전부 고정값 | 미사일들이 한 덩어리로 겹쳐 날아간다 |

**꼬리(trail)를 빠뜨리지 마라.** 원본은 최근 8점을 폴리라인으로 그린다.
선분 뷰도 풀에서 빌리고 **본체가 사라질 때 같이 반납**한다.

**수명 종료 처리도 원본을 본다.** 원본 미사일은 **맞지 않고 수명이 다해도 그 자리에서 폭발하고
splash 를 준다.** 조용히 사라지게 두면 광역 피해가 통째로 빠진다.

## ★ 메인 루프의 게이트 조건을 한 줄씩 옮긴다

**가장 놓치기 쉬운 곳이다.** 함수 단위로 이식하면 루프의 `if` 조건이 통째로 사라진다.

```js
// 원본.html — 메인 루프 본체 (인용할 때 라인 번호를 grep 으로 재확정한다)
if(screen==='combat'){
  drawScene(t,dt);                                   // ← 그리기는 항상 돈다
  if(!(AUG&&AUG.open) && !(G&&G.paused)){            // ← 이 조건이 시뮬 게이트다
    updateCombat(dt);
    …
  }
}
```

> **[사고]** 「선택 모달이 뜨면 시뮬이 멈춘다」는 규칙이 이 한 줄이다.
> 이걸 빠뜨려서 카드를 고르는 사이에 적탄을 맞고 격침당했다.

**규칙**

- 원본 루프 본문을 **줄 단위로 표로 만들고** 각 줄의 조건을 유니티 쪽과 짝지운다.
- 「그리기는 계속 / 시뮬만 정지」인지, 둘 다 정지인지 구분한다. 대개 **그리기는 계속**이다.
- 정지 게이트가 여럿일 수 있다 (모달 · 일시정지 · 결과 · 컷신). **전부 나열한다.**
- 가변 dt는 **원본과 같은 상한으로 클램프** (**[예시]** 0.033 — 원본에서 실측한 값을 쓴다).

**검증** — 모달을 띄운 채 수백 프레임을 흘려보내고 `시각·개체 수·HP` 가 **고정**인지 본다.
**[예시]** 한 프로젝트의 실측 로그:

```
778프레임 경과 · ctx.Time 3.952 고정 · 적 83기 고정 · HP 403.0 고정   ✓
```

부수 효과로 이 상태가 **가장 안정적인 캡처·측정 프레임**이 된다 (공통절차 「교전 중 프레임을 얼려서 본다」).

## ★★ 원본의 **배열 순회 방향은 사양이다**

원본이 **배열을 훑으면서 그 자리에서 고치는** 로직(낙하·전파·연쇄·정렬·확산)은
**순회 방향이 결과를 바꾼다.** 방금 고친 칸을 같은 순회에서 다시 보기 때문이다.

| 원본이 훑는 방향 | 한 번의 호출에서 일어나는 일 |
|---|---|
| **오름차순**으로 훑으며 「다음 칸이 비었으면 옮긴다」 | 하나가 **빈 자리가 이어지는 만큼 끝까지 미끄러진다.** 중간 자리는 비어 남는다 |
| **내림차순**으로 훑으며 같은 일 | 각각 **한 칸씩만** 움직인다 |
| 한 번에 모아 압축 | 줄 전체가 **한 번에** 정렬된다 |

**셋이 전부 다른 결과를 낸다.** 그리고 **화면만 보면 셋 다 그럴듯하다** — 몇 프레임 뒤에는
비슷한 그림이 되기 때문이다. 차이는 **중간 프레임과 연쇄 타이밍**에서만 드러난다.

> **[사고]** 원본이 「위에서 아래로 훑으며 아래가 비었으면 내린다」였다.
> 세로로 빈 칸 3개를 만들자 **말 하나가 세 칸을 한 번에 미끄러지고 중간 두 칸은 빈 채로 남았다.**
> 유니티에서 「열을 훑어 압축」으로 짰으면 같은 입력에 **완전히 다른 보드**가 나왔을 것이다.

**규칙**

- 원본의 **루프 방향과 인덱스 산술을 그대로** 옮긴다. 「같은 결과가 나오게」가 아니라 **같은 절차**다.
- 「더 효율적으로」 모아서 처리하지 않는다. **중간 상태가 사양이다.**
- **정답지로 못 박는다** — 빈 자리를 **연속**으로 만든 입력과 **떨어뜨려** 만든 입력을 각각 재면
  세 방향이 서로 다른 값을 낸다. 이 두 벡터가 방향을 고정한다.

```bash
# 원본에서 제자리 수정 루프를 찾는다 — 방향을 눈으로 확인한다
grep -nE "for *\(.*(i\+\+|i--|--i|\+\+i)" 원본.js
```

## ★★ **먼저 처리한 것이 뒤 판정을 막는다**

원본이 한 루프에서 **판정을 여러 개 돌리면서 즉시 자료를 고치면**,
앞 판정이 지운 자리를 뒤 판정이 **못 보게** 된다. 그래서 **순서가 곧 결과**다.

전형적인 모양은 이렇다 — 판정마다 「이미 처리된 자리」를 걸러내는 가드가 붙어 있다.

```js
// [예시] 첫 칸이 이미 비었으면 건너뛴다 — 앞 판정이 비운 자리다
const isBlank = cells[i] === "";
if (group.every(x => cells[x] === decided && !isBlank)) { … 제거 … }
```

| 겹치는 입력 | 순서를 지키면 | 「잘 만든」 판정이면 |
|---|---|---|
| 큰 패턴과 작은 패턴이 **한 칸을 공유** | **큰 쪽만** 점수가 난다 | 둘 다 나서 점수가 더 크다 |
| 판정 길이보다 **더 긴 연속** | 앞부분만 먹고 **꼬리가 남는다** | 전부 먹는다 |

> **[사고]** 가로 4연속과 세로 3연속이 한 칸을 공유하는 판을 심었더니 **가로 4점만** 났고
> 세로 쪽 두 칸은 판에 그대로 남았다. 「판정을 «교과서대로» 정확히」 구현했다면 7점이 났을 것이다.
> 5연속을 심었을 때도 **4점만** 나고 다섯 번째가 남았다.

**규칙**

- **판정 순서를 원본 함수 호출 순서 그대로** 옮긴다. 묶어서 한 번에 판정하지 않는다.
- **즉시 수정을 나중으로 미루지 않는다.** 「전부 찾아 두고 한꺼번에 제거」로 바꾸면 결과가 달라진다.
- 앞 판정이 남긴 **가드 조건**(빈 자리·처리 완료 표시)을 빠뜨리지 않는다 — 그 한 줄이 순서를 만든다.
- **겹치는 입력을 벡터로 남긴다.** 안 겹치는 입력만 재면 이 차이가 안 잡힌다.

## 조기 반환 가드는 뒤따르는 로직보다 **넓어야** 한다

성능을 위해 앞에 두는 빠른 탈출이 실제 판정보다 좁으면 **일부 입력만 조용히 건너뛴다.**

```csharp
// 틀림 — 정규식은 "/ Lv" 처럼 공백이 낀 것도 잡는데 가드가 "/Lv" 만 본다
if (text.IndexOf("/Lv") < 0) return text;
return LevelScaleRegex.Replace(text, …);
```

전체가 안 되면 금방 알지만, **일부만 안 되면 데이터 탓으로 넘어간다.**

**규칙** — 가드는 판정식의 **가장 느슨한 부분집합**으로 잡는다. 위 예에서는 `"Lv"` 다.
가드를 넣었으면 **가드에 걸리는 케이스와 안 걸리는 케이스를 각각 한 개씩** 실측한다.

## 충돌 · 크기를 상수로 박지 않는다

```js
if(dx*dx+dy*dy < (e.r + s.r + 2)**2)   // 원본 — 양쪽 반지름을 다 본다
```
```csharp
HitTest(s.Position, 10f);              // 틀림 — 탄 반지름을 안 본다
```

탄 반지름은 **종류마다 다르다** (주무기 · 보조 · 요격 · 전용 · 드론이 전부 다른 값).
상수로 두면 큰 적에도 잘 안 맞고 작은 탄은 과하게 맞는다.
**창 배율을 곱해야 한다** — 상대편 반지름은 이미 스케일된 값이다.

원본이 개체에 실어 보내는 반지름(`shots[].r`)을 **그대로 통과시킨다.**
특수탄은 일반탄의 몇 배씩 되기도 한다 — 눈대중 상수를 넣어 2~3배 작았던 사례가 있다.

## 회전은 여러 번 겹쳐 걸린다

```js
drawEnemy:       ctx.rotate(e.angle)      // e.angle = π/2 (스폰 시)
drawEnemySprite: ctx.rotate(Math.PI/2)    // 스프라이트 '위' → +x 정렬
// 합 = π → 앞머리가 화면 아래(플레이어)를 본다
```

| 대상 | 원본 회전 | 틀렸을 때 |
|---|---|---|
| 적 | `e.angle + π/2` = **180°** | 등을 보이고 내려온다 |
| 호위 드론 | `atan2(ownerY−dr.y, ownerX−dr.x) + π` (주체 **바깥**) | 전부 오른쪽만 봐 커서 아이콘처럼 보인다 |

**점검법**: 그 draw 트리에서 `rotate(` 를 **전부** 찾아 합산한다.

**스프라이트가 향하는 축을 프로젝트에서 하나로 통일한다.**
`+x` 로 구웠으면 회전은 `atan2(vy,vx)` 그대로다. 어떤 뷰만 `−90°` 를 붙이면 반드시 한쪽이 틀어진다.

## 수치 계층

- 계산은 **double**. 원본 JS 숫자는 전부 double이다.
- float를 쓰면 상대오차가 남는다 — **[예시]** 실측 **1.3e-7** (`gunDmg` 1944.4539975 → 1944.45374).
  표시에는 영향 없지만 정답지 1e-9 판정은 못 넘는다.
- 확률은 **주입식 RNG만**. 언어 기본 난수 직접 호출 금지 (재현 불가 = 채점 불가).
- 물리 엔진 혼입 금지 — 판정은 자체 코드다.
  **단, 원본이 «물리 엔진 위에서» 도는 경우는 반대다** — 아래.

#### ★ 원본이 물리 엔진을 쓰면 규칙이 뒤집힌다

「물리 엔진 혼입 금지」의 이유는 **원본에 없는 거동이 엔진에서 새로 생기는 것**을 막기 위함이다.
그런데 **원본 자체가 물리 엔진 위에서 도는 웹 게임**이 있다 (Box2D 계열이 흔하다).

> 물리 상수·스텝 순서를 캐는 법은 **`공통절차.md` 「런타임에서 직접 캐내는 법」**이 정본이다.
그때는 **엔진을 안 쓰는 쪽이 오히려 원본에서 멀어진다.**

| 먼저 확인한다 | 어떻게 |
|---|---|
| 원본이 물리 엔진을 쓰나 | 런타임 인스턴스의 **거동/컴포넌트 목록**을 뒤진다 (`공통절차`·PD 「런타임을 먼저 찔러라」). 쓰고 있으면 **반발·마찰·밀도·감쇠·충돌 도형·월드 중력이 전부 «읽힌다»** — 재지 말고 읽어라 |
| 엔진 계열이 같은가 | 엔진이 같은 계열이면 **파라미터가 1:1 로 매핑**된다 |

**같은 계열이면 «실측 파라미터로» 엔진을 쓰는 것이 재구현보다 원본에 가깝다.** 단 셋을 지킨다.

1. **엔진 스케일을 원본과 맞춘다.** 물리 엔진은 **절대 크기에 의존하는 내부 상수**를 갖는다
   (접촉 슬롭 · **반발이 죽는 속도 임계** 등). 원본이 「1 미터 = N 픽셀」로 돌면 **우리도 그 스케일**이어야
   «같은 지점에서 안 튀기 시작»한다. 스케일이 어긋나면 **다중 충돌 뒤 안정화가 원본과 갈린다** —
   그리고 그 차이는 **단발 궤적 검사로는 안 잡힌다.**
2. **채점을 실제 경로에서 한다.** 엔진을 쓰면 헤드리스 계산만으로 채점할 수 없다 —
   **재생 모드 검사**로 옮긴다 (`공통절차`). 이건 손해가 아니라 「하네스가 실제 경로를 지난다」로 가는 것이다.
3. **파라미터를 «맞추지» 말고 읽는다.** 정답지가 통과하도록 반발·마찰을 고르는 것은 **없는 실측을 지어내는 것**이다.

> ⚠ **접선(마찰) 거동은 「계수 하나」로 재현되지 않는다.** 회전 관성이 붙으면 같은 충돌에서도
> 접선 속도비가 크게 흩어지고 **각속도 부호까지 바뀐다.** 「반사 벡터로 튕기는 점」 모델은
> **원리적으로** 이걸 못 낸다 — 원본이 회전하는 강체를 쓰면 우리도 그래야 한다.

## ★★ 밸런싱은 «범위를 물어» 채록하고, 규칙은 **채록 밖에서** 검증한다

레벨·스테이지·웨이브가 있는 게임에서 **1레벨만 맞추고 끝내는 것이 가장 흔한 미완성**이다.
배치도 그림도 조작도 맞는데 **「원본보다 쉽다/어렵다」**가 남는다 — 그리고 이건 정적 캡처에 안 잡힌다.

**전수는 비용이 폭발하고, 1개는 규칙이 안 나온다.** 그래서 **범위를 확정표(11-b)로 못 박고 시작한다.**

| 단계 | 무엇을 |
|---|---|
| ① **묻는다** | 「앞 몇 개 레벨까지 원본과 똑같이 맞출까요?」 — PD 가 착수 질문에서 받는다 |
| ② **채록** | 그 범위를 **전부** 원본에서 실측한다. 「대표 몇 개」로 줄이지 않는다 |
| ③ **규칙 도출** | 채록값에서 공식·표를 뽑는다 |
| ④ ★ **채록 밖 검증** | **도출에 안 쓴 레벨**로 공식을 검산한다 (홀드아웃) |

### ★ ④가 없으면 규칙이 아니라 **암기**다

채록 N개에 맞는 공식은 언제나 만들 수 있다 — **N개에 맞았다는 사실은 아무것도 증명하지 않는다.**
채록에 안 쓴 레벨에서 맞아야 규칙이다.

> **채록 개수를 정할 때 «검증용 몫»을 미리 떼어 둔다.** 전부 도출에 쓰면 검산할 것이 안 남는다.

⚠ **홀드아웃을 통과해도 «규칙»의 등급은 ②(실측)까지다.** 같은 채록을 내는 다른 기전이 있을 수 있다 —
실제로 「고정 간격 + 가중치 뽑기」와 「위협 예산」이 같은 스폰 곡선을 냈다. 규칙을 ①로 올리는 것은
**소스 직독 · 함수 후킹 · 죽일 조건을 건 가설 시험** 셋 중 하나뿐이다 (PD 「근거 등급」 · 재발방지 `#128`).

### ★★ 자유 피팅은 **「데이터마다 다르다」로 오독시킨다**

파라미터를 전부 풀어 놓고 각 레벨에 따로 맞추면 **레벨마다 다른 값**이 나온다.
그러면 「이건 레벨 데이터구나」로 읽고 **레벨표에 N벌을 적게 된다** — 그리고 그건 틀린 결론이다.

> **[사고]** 발사점 보정을 레벨별로 자유 피팅하니 진폭이 레벨마다 달라져 「레벨 데이터」로 읽혔다.
> **절편을 이미 아는 값으로 고정**하고 나머지 하나만 맞추자 **전 레벨이 한 값**에 잔차 0.07 이내로 들어왔다.
> 범인은 레벨이 아니라 **모델 범위 밖의 표본 한 점**이었다.

**규칙** — 자유도를 **먼저 줄이고** 맞춘다. 이미 실측으로 아는 항은 **고정한다.**
자유도를 다 풀면 «무엇이든» 맞고, 맞았다는 사실이 정보를 잃는다.

### ★ 「난이도가 같다」는 배치가 아니라 **성공 범위**로 잰다

레벨 배치를 픽셀 단위로 옮겨도 난이도는 안 옮겨진다. 재는 값은 **그 레벨을 깨는 입력의 범위**다.

| ✗ 이렇게 재면 안 잡힌다 | ✓ 이렇게 잰다 |
|---|---|
| 배치·좌표 일치율 | **입력을 격자로 훑어 성공/실패를 원본과 «격자점마다» 대조** |
| 「깨진다/안 깨진다」 | **깨지는 입력 «구간»의 시작과 끝** |
| 한 번 깨봤다 | 격자점마다 **n 회** — 원본이 갈리는지도 같이 본다 |

⚠ **성공 범위는 비율로 비교하지 않는다.** 우리 쪽 구간 개수가 분모를 바꾼다 —
축은 **갈린 격자점 수**다.

## ★★ 원본이 **스스로도** 재현하지 못하는 구간이 있다

**정답지의 대전제는 「같은 입력이면 원본이 같은 답을 낸다」**인데, 이 전제가 깨지는 구간이 있다.

> **[사고]** 같은 세기로 두 번 쐈다. 발사 위치가 **0.001 px 이내로 동일**하고 속도·회전도 같았다.
> 그런데 **한쪽만 골인**했다. 네 번째 접촉까지 똑같이 가다가 **모서리를 스치는 다섯 번째 접촉에서
> 33 ms 어긋나고** 그 뒤로 완전히 다른 경로가 됐다. 씨앗은 원본의 **들쭉날쭉한 프레임 간격**이었다.

**웹 원본은 프레임 간격이 고정이 아니다.** 그 미세한 차이가 **스침·저속 정착·다중 접촉**에서 증폭된다.

| 무엇 | 어떻게 |
|---|---|
| **판정** | 같은 입력을 **n 회**(≥3) 돌려 결과가 갈리는지 본다. **2회로는 부족하다** |
| **분류** | 갈리는 벡터는 **지우지 말고 「비결정」으로 «분류»**한다 — 왜 채점 대상이 아닌지가 기록이다 |
| **채점** | 채점기가 그 구간을 불일치로 세지 않게 하되 **「비결정 N건 제외」를 리포트에 반드시 찍는다** |
| **정답지 고르기** | 정답지는 **짧게 결판나는 샷**으로 고른다 — 접촉이 적고 빨리 끝나는 것 |

### ⚠⚠ 이것을 **면죄부로 쓰면 그 순간 규칙이 무너진다**

「원본이 갈리니까 우리 차이는 결함이 아니다」는 **가장 달콤한 오용**이다.

- **원본이 갈린다는 것부터 «재서» 확증한다** — 우리가 안 맞는 자리를 보고 추측하지 않는다
- **갈리는 빈도를 잰다** — 원본이 10회 중 9회 성공하는데 우리가 0회면 그건 **우리 결함**이다
- **제외 범위를 넓히면 그게 곧 「점수를 근거로 값을 고르는 것」**이다 (`재발방지` 참조)
- 제외한 건수는 **항상 따로 보고**한다. 조용히 빼면 커버리지를 속인 것이 된다

### 정답지 — 수치 환원을 증명하는 유일한 수단

원본을 N가지 상태로 돌려 계산 결과 전 필드를 덤프해 둔 정답지.
계산은 유니티가 하지만 **정답지가 없으면 「대충 비슷하다」 말고는 증명 수단이 없다.**
없으면 공통절차 「A/B 측정」의 A/B 개체 수 판정으로 대체한다.

#### ⓪ 이건 **프로젝트가 직접 만드는 것**이다 — 어디서 받아오는 게 아니다

정답지(json)도, 채점기(cs)도 **이 프로젝트에서 새로 만든다.** 소유와 시점을 못 박는다.

| 무엇 | 누가 | 언제 |
|---|---|---|
| 원본을 헤드리스 브라우저로 돌려 **정답지 덤프** | **Transfer_Programmer** (Client 지식 기반) | **G2 를 열기 전** |
| 파서 · 필드 대응 · 채점기 · 에디터 메뉴 (`.cs`) | **Transfer_Programmer** | 같이 |
| 어느 상태를 몇 개 뽑을지 (스위트 설계) | Client 지식이 `02_시스템_*.md` 로 넘긴다 | 학습 단계 |

- **하네스를 만드는 것 자체가 리스트업 항목이다.** 「스탯 환원」 항목 아래 묻지 말고
  **별도 항목으로 올린다** — 안 그러면 영원히 「나중에」가 된다 (PD 「재는 도구를 먼저 만든다」).
- 하네스가 없는 동안 그 수치 항목은 **`미측정(③ 하네스 없음)`** 이고 달성률 **0%** 다.
  통과가 아니다 (분석로직 「섹션별 기입 규칙」).
- **전제** — 정답지는 **임의 키 수백 개짜리 맵**이라 임의 키를 담는 역직렬화 수단이 필요하다
  (Unity 내장 `JsonUtility` 로는 못 읽는다). 무엇을 쓸지는 프로젝트가 고른다 —
  선택지와 접점 격리는 [DataFramework 「전제」](DataFramework.md).

구현은 둘로 나눈다. **정답지(데이터)와 채점기(도구)는 수명이 다르다.**

| 자리 | 무엇 | 수명 |
|---|---|---|
| 정답지 JSON | N벡터. **원본을 헤드리스 브라우저로 돌려 뽑는다** | 프로젝트와 함께 남는다 |
| 채점기 (에디터 메뉴) | 정답지를 읽어 이식본과 대조 | 도구다. 지워질 수 있다 |

> ⚠ **채점기가 없는 동안 수치 변경은 「증명 수단이 없는 상태」다.**
> 정답지만 남고 채점기가 사라진 상태를 「검증됨」으로 읽지 않는다 —
> 스탯 계통을 다시 손대게 되면 **채점기를 먼저 복원해 돌린 뒤** 고친다.
> 이 절의 방법론은 그때 그대로 쓴다.

#### ⓐ 순서를 지킨다 — 출처 대조가 채점보다 먼저다

정답지는 **어떤 시점의 원본 데이터**를 전제로 뽑혔다. 그 전제가 깨진 채 채점하면
실패가 전부 「계산이 틀렸다」로 보이고, 멀쩡한 계산을 몇 시간 뒤진다.
**출처 대조기**를 먼저 돌린다 — 노드 수·유닛 코드·정답지가 주입하는 키가 지금 데이터에 다 있는지부터 본다.

> **여기서 「전부 일치」를 못 찍으면 그 뒤 실패는 읽을 수 없다.**
> 계열별 노드 수가 정답지 메타와 같고 주입 코드가 전부 존재해야,
> 그다음 실패를 「계산이 틀렸다」로 해석할 자격이 생긴다.

#### ⓑ 이름 대응은 규칙 두 개 + 예외표로 끝난다

원본 JS는 camelCase, 이식본은 PascalCase다. **[예시]** 한 프로젝트의 실측 —
**310키 중 296키가 규칙만으로 맞았다.** 나머지도 `_xxxDed → XxxDedicated` 규칙 하나로 13건이 풀렸다.
이식이 필드 단위로 원본을 따라갔으면 대응표를 손으로 쓸 일이 거의 없다 —
**예외가 많으면 대응표가 아니라 이식을 의심한다.**

**대응 필드가 없으면 조용히 건너뛰지 않는다.** 「대응 필드 없음」으로 따로 세어 보고한다.
안 재면 없는 줄도 모른다 — **[예시]** 이 규칙이 실제로 미이식 필드 하나를 잡았다
(원본 `s.guidedMult`(2948)를 이식본이 `GuidedMul` 하나에 겸해 쓰고 있었다).

#### ⓒ 실패를 세 갈래로 갈라 놓고 시작한다

한 덩어리로 보면 못 고친다. 채점기가 상대오차 분포를 같이 찍는 이유다.

| 갈래 | 신호 | 처방 |
|---|---|---|
| **자료형 한계** | 상대오차 1e-9 ~ 1e-6 구간에 몰림 | float → double. 계산은 안 건드린다 |
| **진짜 계산 차이** | 1e-6 초과 · 특정 스위트/필드에 집중 | 원본 라인과 대조 |
| **정답지 쪽 결함** | 기대값이 모든 벡터에서 같은 이상값 | 비교에서 빼고 **왜 뺐는지 적는다** |

> **[예시]** 한 프로젝트의 실측 1회차: 비교 79,897필드 중 완전일치 77.7% · **1e-9~1e-6 구간 12,748** · **1e-6 초과 754**.
> 즉 「float 때문에 못 넘는 것」이 「진짜 틀린 것」의 17배였다.
> 이 분포를 안 찍었으면 754건을 12,748건 속에서 못 찾는다.

#### ⓓ 정답지도 틀린다 — 「기대값이 전 벡터 동일」이면 생성기를 의심한다

**[예시]** 한 프로젝트의 실측 — `stats._syn`이 230벡터 전부 `{}`였다. 원본이 `s._syn = new Set()`이고
`JSON.stringify(new Set([...]))`는 **언제나 `{}`**라서다.
융합을 6종 다 켠 벡터(`GV043 전투 트리 전체 max`)조차 `{}`로 찍혔다.

**이식본이 옳게 6종을 켠 것이 실패로 찍혔다.** 그대로 뒀으면 진짜 결함 위에 71건의 가짜 실패가 덮인다.
생성기가 `Array.from()`으로 바꿔 다시 뽑기 전까지는 **측정 불가 필드**로 빼고 그 사실을 코드에 적는다.

`Set` / `Map` / 함수 / `undefined` / `NaN` / `Infinity`가 JSON을 못 건너오는 대표 사례다.
**정답지를 뽑을 때 이 다섯을 먼저 훑는다.**

#### ⓔ 입력에 안 적힌 암묵 상태를 같이 옮긴다

정답지 입력은 **원본이 로드할 때 채우는 기본값을 적지 않는다.**
보유 목록이 비어 보이는 벡터도 원본 런타임에서는 **기본 지급분이 항상 들어간다**
(`if(!owned.default) owned.default = 1` 류의 한 줄이 `boot()` 근처에 있다).

이걸 빼먹으면 보유 수가 1 적게 세어져 **보유 보너스 계통이 통째로 빠지고**,
그 계열 벡터가 전멸한다. 규칙을 하네스에 베껴 쓰지 말고
**이식본의 기본값 채우기를 다시 태워라** — 그래야 그 규칙 자체도 같이 검증된다.
(상태 주입 뒤 로드 완료 이벤트를 한 번 더 쏘는 것으로 해결된다.)

#### ⓕ 하네스는 사용자 세이브를 건드릴 수 없어야 한다

「안 건드리게 조심한다」가 아니라 **경로를 없앤다.**

- 상태 주입은 파일을 읽지도 쓰지도 않는 전용 API로만 한다
  (**[예시]** `SaveManager.InjectVolatile` — 주입과 동시에 저장 가능 플래그(`SaveReady`)를 꺼
  이후 저장을 무효화한다. 이름은 프로젝트가 정한다).
- 데이터·매니저는 하네스가 세우지 않는다. **`GameInitialize` 가 세운 것을 그대로 쓴다** —
  그래서 하네스는 **재생 중에만** 돈다 (Play → 인트로에서 게임 시작 → 로딩 완료 뒤 실행).
  중복 기동 경로(`DataManager.InitializeFromJson` 직접 호출·`GameManager` 자체 생성)를 없앴다.
  에디트 모드에서 `GameManager.Instance` 를 억지로 만들면 이전 세션에서 남은
  `MonoSingleton._isDestroyed` 에 걸려 영구히 null 이 나오던 함정도 같이 사라진다.
- **재생 중 여부를 보는 가드는 메뉴가 아니라 상태를 만지는 함수에 건다**
  (**[예시]** `GoldenHarness.RequirePlayMode` — 이름은 프로젝트가 정한다).
  메뉴 가드만 두면 우회해 직접 부를 수 있다 — 실제로 그런 적이 있다.
- 파일이 무사한 건 위의 `SaveReady` 차단 덕이지 가드 덕이 아니다.
  **돌아가는 세션의 메모리 상태는 갈아엎힌다** — 채점한 세션은 버리고 Play 를 다시 켠다.

### 미리보기 계산은 「실제로 적용했다가 되돌린다」

원본이 그렇게 한다. 예: 「이 강화를 받으면 뭐가 바뀌나」 표는 실제로 획득시켜 스탯을 두 번 계산한다.

```js
const A=computeStats();
AUG.act.add(k); AUG.stk[k]=stk+1;     // 받은 상태로 만든다
const B=computeStats();
AUG.stk[k]=stk; if(!wasAct) AUG.act.delete(k);   // 원복
```

**원복을 빠뜨리면 실제 스탯이 오염된다.** 조기 `return` 경로에서도 원복되는지 확인한다.
캐시가 있으면 **두 계산 사이에 무효화**하고, 끝나고 한 번 더 무효화한다.

## 데이터 접근

- 자동 생성 파일은 **직접 수정 금지**. 원본(엑셀)이나 제너레이터를 고친다.
- 콘크리트 컨테이너를 만들거나 지우면 **익스포터를 다시 돌린다** (접근자 코드젠이 스캔한다).
- `Id` 가 아닌 컬럼으로 조회해야 하면 컨테이너에서 자료구조를 직접 만든다
  (로드마다 새로 만들고 행마다 채우는 훅). 로컬 캐시를 따로 들지 않는다.
- **테이블을 추가했으면 조회가 성공하는지 실측한다** — 기획 파트 「스탯이 안 물려 있다」 참고.

## 클라 파트 완료 체크리스트

- [ ] **미측정 항목 0** — 못 잰 것은 `미측정(사유)` 로 적고 **재측정 대기**에 등록했다
- [ ] **내 권한 밖 파일을 건드리지 않았다** (PD 「역할 기동 규약」 권한표)

1. 원본에서 계산 결과가 들어가는 자리를 전수 나열하고 전부 도달하나 (「스탯이 안 물려 있다」)
2. UI로 넘기는 구조체에 **안 쓰이는 필드가 없나** (「스냅샷 구조체는 안 쓰는 필드가 있으면 계약」)
3. 원본에 없는 상한을 넣지 않았나 (「원본에 없는 상한」)
4. `t`/`dt` 를 받는 원본 함수가 유니티에서 실제로 움직이나 (「거동이 빠졌다」)
5. **메인 루프의 게이트 조건을 전부 옮겼나** (「메인 루프의 게이트 조건을 한 줄씩 옮긴다」) — 모달·일시정지·결과·컷신
6. 조기 반환 가드가 판정식보다 넓은가 (「조기 반환 가드는 뒤따르는 로직보다 넓어야」)
7. 충돌·표기 크기가 원본 변수인가 (「충돌 · 크기를 상수로 박지 않는다」)
8. `rotate(` 를 전부 합산해 방향을 맞췄나 (「회전은 여러 번 겹쳐 걸린다」)
9. 계산이 double이고 RNG가 주입식인가 (「수치 계층」)
10. 미리보기 계산의 원복이 모든 경로에서 도나 (「미리보기 계산은 실제로 적용했다가 되돌린다」)
11. 새 테이블의 컨테이너 조회가 실제로 성공하나 (「데이터 접근」)
