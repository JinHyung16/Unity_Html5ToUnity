## 착수하면 가장 먼저 하는 일 — 그리기 파라미터 전수표

코드를 고치기 전에 원본의 모든 그리기 파라미터를 표로 뽑는다. 표의 빈 칸이 남은 일이다.

```bash
grep -n "globalCompositeOperation" 원본.html    # 합성 모드 — 어느 캔버스인지까지 구분
grep -n "lineWidth" 원본.html                   # 선 굵기 (절대 픽셀이다)
grep -n "shadowBlur\|shadowColor" 원본.html      # 글로우
grep -n "globalAlpha" 원본.html                 # 알파
grep -n "createRadialGradient\|createLinearGradient" 원본.html
```

| 대상 | 원본 값 | 원본 라인 | 우리 값 | 상태 |
|---|---|---|---|---|
| 예: 노바 링 | `lineWidth 4.5` · `shadowBlur 14` | 5231 (grep 으로 재확정) | 4.5 + 소프트링 | 통과 |

## 합성 모드 — 프로젝트 기본값이 원본과 반대일 수 있다

원본 합성 모드를 그 컨텍스트 기준으로 확정한다. 캔버스는 프레임 시작에 정규화하는 경우가 많고, 파일의 `'lighter'` 가 다른 캔버스(컷신·인트로 `ctx`) 것일 수 있다.

```js
// 원본.html — 전투 그리기 진입 첫 줄 (라인은 grep 으로 재확정)
bx.globalCompositeOperation='source-over';   // 이후 끝까지 안 바꾼다
```

사례: 도형 컴포넌트의 `_additive = true` 기본값 때문에 탄환·링·보호막이 전부 가산으로 하얗게 탔다.

- **원본에 없는 렌더 기능은 기본값도 꺼 둔다.** 안 쓰기로 했으면 코드에서 지운다(스위치를 남기면 누군가 켠다).
- 프리팹에 남은 옛 머티리얼은 런타임에서 되돌리는 안전장치를 둔다.
- 활성 렌더러를 전수 세어 가산 0 을 실측한다 (예: `활성 SpriteRenderer 70개 → 전부 Sprite-Lit-Default (가산 0)`).
- 발광은 가산이 아니라 `shadowBlur` 로 내고, 아트에 이미 구워져 있다(「글로우」).

## 글로우 — `shadowBlur` 는 수식이 있다

`shadowBlur = b` 는 도형 알파를 σ = b/2 가우시안으로 흐려 도형 아래에 깐다.

### 작은 도형은 봉우리 알파가 크게 내려간다

```
peak ≈ 1 − exp(−(r/σ)²/2)      // 반지름 r 원판의 중심 알파
```

`r=7, σ=6` 이면 0.49다. 상수 알파(예: 0.75)를 깔면 글로우가 두 배 밝아진다.

### 눈대중 배율 대신 수치 적분해서 굽는다

원판을 가우시안으로 흐린 반경 프로파일을 수치 적분해 굽는다. 결과는 `k = σ / 도형반지름` 에만 의존하므로 k 계열로 굽고 런타임이 최근접을 고른다.

```
텍스처 반경 = 도형반지름 × (1 + 3k)     // 가우시안 3σ 까지
알파는 프로파일이 들고 있으므로 런타임 tint 알파는 1
```

**이론식과 소수 3자리까지 맞아야 베이크를 믿는다.** 실측은 프로젝트마다 다시 잰다.

| k = σ/반지름 | 0.35 | 0.50 | 0.70 | 1.00 | 1.40 | 2.00 |
|---|---|---|---|---|---|---|
| 실측 peak (예) | 0.984 | 0.863 | 0.639 | 0.392 | 0.224 | 0.118 |
| 이론 `1−exp(−(1/k)²/2)` | 0.983 | 0.865 | 0.640 | 0.393 | 0.225 | 0.118 |

#### 수식이 맞아도 인자 단위가 틀리면 전부 어긋난다

호출부는 σ 가 아니라 원본 `shadowBlur` 를 넘기고 헬퍼가 `σ = blur/2` 로 바꾼다. 여기서 단위가 갈린다.
사례: `shadowBlur / r * 2` 를 넘겨 σ 가 두 배가 됐고, 증상은 「탄환 글로우가 쨍하다」뿐이었다.

**단위 규칙을 헬퍼 주석에 못박는다.** 다른 보정은 없다. `*2`·`/2` 가 붙어 있으면 그 자체가 신호다.

| 생성기 | 로컬 단위 | 넘기는 값 |
|---|---|---|
| 원본 픽셀 좌표 (장비 프롭) | 1 = 1 CSS px | `shadowBlur` 그대로 |
| 반지름 정규화 (엔티티 생성기) | 1 = 원본 `r` | `shadowBlur / r` |

판정은 구운 PNG 의 알파 프로파일로 한다 (UIUX 「절차 생성 도형은 구운 PNG의 알파를 직」). 예: σ 두 배면 2.0r 알파 6, 정상은 0.
σ 를 반으로 줄이면 바깥 번짐이 사라지고 본체는 진해진다(`peak = 1 − exp(−(halfWidth/σ)²/2)` 상승). 「글로우를 줄였는데 총 알파가 늘었다」는 정상이다.

### 레이어 수를 센다 — 「글로우가 세다」의 진짜 원인은 대개 본체 누락

**발광이 과해 보이면 글로우를 줄이기 전에 레이어 수부터 센다.** 원본 겹 수와 우리 렌더러 자식 수를 맞춘다.

```js
// 원본 아군 탄 (5691 — 라인은 grep 으로 재확정) — 세 겹이다
shadowColor=pcol; shadowBlur=_bl;                    // 1 글로우
fillStyle=pcol; ellipse(0,0,_pr2+3,_pr2-1); fill();  // 2 본체 타원
shadowBlur=0;
fillStyle='#eaffff'; arc(0,0,_pr2*0.5); fill();      // 3 밝은 코어
```

사례: 1·3만 그리고 2(본체)가 빠져 「글로우가 세고 퀄이 낮다」로 보였다.

| 세는 법 | 명령 |
|---|---|
| 원본 | 그 draw 블록의 `fill()` · `stroke()` · `drawImage(` 호출 수 |
| 우리 | 그 Visual 프리팹의 `SpriteRenderer` 자식 수 |

## 선 굵기는 절대 픽셀이다

원본 링·테두리는 고정 픽셀 스트로크다. 반지름 비례로 구우면 큰 반지름에서만 틀어진다.
사례: 「굵기 = 지름의 16%」로 구운 링이 반지름 200 오라에서 64px(원본 1.5px)로 나왔다.

「굵기 / 반지름」 비율 계열로 굽고 런타임이 **로그 거리**로 최근접을 고른다. 선형 거리는 등비 계열에서 큰 쪽에 쏠린다.

```
ratios = { 0.006, 0.012, 0.024, 0.048, 0.096, 0.192, 0.384 }   // 등비 — 계열 값은 프로젝트가 정한다
고를 때: wanted = lineWidth / radius,  거리 = |log(ratio) − log(wanted)|
```

- 얇은 띠 텍스처는 512 이상으로 굽는다. 128px 를 400px로 늘리면 깨져 보인다.
- `shadowBlur` 가 붙은 스트로크는 두 겹이다. 넓은 소프트 링을 아래, 또렷한 선을 위에 둔다(원본은 `stroke()` 한 번).

## 절차 이펙트는 재구현하지 말고 원본에서 베이크한다

사례: 원본 3프레임 실측에서 손으로 다시 그리면 최대 Δ183, 원본 렌더 결과를 추출해 구우면 Δ0 이었다.

- 원본 드로잉 코드를 줄 단위로, 캔버스 API를 그대로 받는 2D 페인터로 옮긴다 (`FillRoundRect` · `StrokePolyline` · `Paint.LinearY/Radial` · `Halo`(=`shadowBlur`) 등).
- **색이 데이터로 갈리는 것만 흰색+알파로 굽고, 나머지는 색까지 굽는다.**
- 원본이 쓰는 폰트·SVG도 원본을 렌더해 가져온다. 손으로 다시 그리지 않는다 (예: 아이콘 92종을 브라우저에서 원본 SVG로 렌더해 아틀라스로 뽑았다).
- 굽는 쪽 상수와 고르는 쪽 상수는 두 파일에 나뉜다. 서로 주석으로 가리키고 같이 바꾼다. 어긋나면 크기가 조용히 틀어진다.

## 애니메이션 — 정적 PNG로는 연출이 사라진다

원본 함수 인자에 `t` · `dt` 가 있으면 움직이는 것이다.

| 원본 형태 | 옮기는 법 |
|---|---|
| `0.5 + 0.5·sin(t·ω)` 맥동 | 골(pulse=0)·마루(pulse=1) 두 장을 굽고, 마루를 위에 얹어 알파 0→1 을 흔든다(크로스페이드). 주기 = `2π/ω` |
| `rotate(t·ω)` 등속 회전 | 회전 요소만 따로 굽고 회전 컴포넌트 |
| `rotate(sin(t·ω)·A)` 왕복 | 별도 레이어 + 사인 회전 컴포넌트 |
| `(t·k) % m` 스캔선·타일 | 별도 레이어 + 드리프트 컴포넌트 |

- 맥동은 대부분 크로스페이드로 끝나고, 회전·이동만 별도 레이어가 필요하다.
- 범용 트윈 라이브러리를 짜지 않고 최소 컴포넌트를 하나씩 만든다.
- UI 버튼의 배율 움직임(펄스·호버·상태)은 [UIFramework](UIFramework.md) 「UI 연출」의 최소 세트를 쓴다. 배율을 곱하는 것이라 크로스페이드가 아니다.
- 방향·속도·순환 폭(이미지 높이)·왕복 여부는 원본 값을 쓴다. 사례: 원본 1.1px/s 배경 드리프트를 `11px/s` 로 넣었다.

### 「어느 쪽을 보나」는 상태다 — 매 프레임 다시 재지 않는다

```js
// 모양만 본다 — 값·이름은 원본마다 다르다
dx < 0 ? sprite.scale.x = -Math.abs(sprite.scale.x)
       : dx > 0 && (sprite.scale.x = Math.abs(sprite.scale.x))
```

`dx === 0` 분기가 없어 안 움직이면 마지막 방향을 둔다. 흔히 거리 게이트(「거리가 N 을 넘을 때만」) 안에 있다.

**방향은 시뮬(모델)이 상태로 들고, 뷰는 부호만 준다.** 게이트·0 분기도 같이 옮긴다.

| 잘못 옮기면 | 증상 |
|---|---|
| 뷰가 매 프레임 `대상.x > 나.x` 를 다시 잰다 | 붙었을 때 부호가 프레임마다 뒤집혀 떤다 |
| 게이트를 빼먹는다 | 같은 증상. 멈춰 있을 때·겹쳤을 때만 난다 |
| 「0 이면 유지」를 빼먹는다 | 세로로만 갈 때 방향이 초기값으로 돌아간다 |

반전 호출부를 전수로 센다. 개체는 다 있으므로 「빠진 개체」 검사에는 안 걸린다.
사례: 반전 자리 다섯(주인공·잡몹·보스·동물·동료) 중 둘만 옮겨 주인공이 반대쪽을 봤다 (재발방지 #160 · #172).
재는 법: 재생에서 배율 x 를 프레임마다 찍어 입력(이동) 부호와 변화 횟수가 같은지 본다. 한 번도 안 바뀌면 반전이 없는 것이다.

### 정지 프리뷰로는 애니메이션 상태를 못 본다 — 페이즈 강제 진입 훅을 표준으로 둔다

프리뷰 하네스는 한 프레임만 굽기 때문에 여러 페이즈 연출은 첫 프레임만 증명된다.
사례: 10연 뽑기 카드가 안 뒤집혔는데 정지 캡처는 뒤집기 전이 정답이라 몇 턴째 정상으로 보였다.

**연출을 붙일 때 페이즈 진입점을 같이 만든다.**

```csharp
#if UNITY_EDITOR
/// <summary>프리뷰·검수용 — 페이즈를 건너뛰고 그 상태로 바로 앉힌다. 트윈은 끝난 값으로 확정한다</summary>
public void EditorSetPhase(Phase phase) { ... }
#endif
```

1. 모든 페이즈에 이름이 있다(「연출 중」 하나로 뭉뚱그리면 진입점을 못 만든다).
2. 진입 시 트윈을 끝난 값으로 확정한다(중간값이면 캡처가 매번 달라 대조가 안 된다).
3. 프리뷰가 페이즈마다 한 장씩 굽고, 원본도 같은 페이즈로 찍어 짝을 만든다(`capture_*.js` 에 단계별 캡처).

## 색공간 — 프로젝트당 한 번 결정하고 그에 맞춰 전부 짠다

캔버스는 감마(sRGB)에서 합성한다. 유니티가 Linear면 `src·a + dst·(1−a)` 를 리니어 값으로 계산해, 반투명이 겹치는 자리의 결과가 달라진다. 불투명 단일 레이어는 문제없다.
「Vertex Color Always In Gamma」 류 옵션과는 무관하다(버텍스 컬러 인코딩 문제이고 블렌딩 수식은 그대로다. 예: 이 저장소의 Unity 6000.3 + URP 에는 그 설정이 없다).
사례: 알파 합성(남색 + 앰버 α0.6) 캔버스 R 157, Gamma 예측 157.0, Linear 예측 203.6.

Linear로 확정된 프로젝트에서는 알파를 역산한다. 베이크 스프라이트는 굽는 마지막에 알파만 바꾼다(`a=1` 은 안 변해 실루엣이 보존된다).

**역산은 한 헬퍼에서 한다.** 호출부에는 원본 감마값을 그대로 두고 헬퍼가 변환한다. 이유: 원본 숫자가 코드에 남아야 대조할 수 있다.

어디가 뜨는지는 픽셀로 특정한다. UI 판은 대개 맞고 반투명이 여러 겹 쌓이는 자리만 뜨므로 거기만 고친다.
색·알파는 원본 `:root` 변수에서 가져오고 하드코딩하지 않는다.

#### 역산은 두 방향이다 — 오버레이가 밝은가 어두운가로 갈린다

리니어 합성은 둘 다 감마보다 밝게 끝난다. 밝은 것은 더 밝아지고, 어두운 것은 덜 어두워진다.

| 오버레이 | 리니어가 내는 결과 | 같게 보이려면 |
|---|---|---|
| 밝은 것 (가산 · 발광 · 밝은 색 판 · 밝은 반투명 선) | 감마보다 밝다 | 알파를 내린다 — `a^2.2` (CSS .5 → 대략 .22~.3) |
| 어두운 것 (딤 · 그림자 · 어두운 판) | 감마보다 덜 어둡다 | 알파를 올린다 — `1 − (1−a)^2.2` |

주의: 정확한 값은 배경색에 달렸고 닫힌 해가 없다. 위 식은 감마 2.2 근사다. 기준 배경 한 색(그 게임이 실제로 덮는 색, 보통 지형 바닥)을 정해 채널별로 정확히 풀고 평균을 쓴다. 아주 밝거나 어두운 배경에서는 몇 단위 어긋난다.
예: 지형 `#64779B` 기준 감마 α.5 → 리니어 α.76 (채널별 .750 / .759 / .771).

사례: 딤을 감마값 그대로 둬 `#64779B` 위 검정 α.5 가 원본 `#323C4E` 대신 `#47556F` 로 밝게 떴다.
버튼 둘레 반투명 띠(「버튼 주변 어두운 글로우」 지적)는 사람 확정으로 걷었다 (재발방지 #184 — 사람이 정한 것을 측정으로 뒤집지 않는다).

## 카메라 · 정렬

**카메라 간 렌더 순서는 `depth` 가 정하고, depth 가 같으면 비결정적이다.** 카메라가 다르면 `sortingOrder` 는 소용없다. UI가 월드 위로 안 올라오면 여기부터 본다.
사례: 월드·UI 카메라가 둘 다 depth −1 이라 월드가 HUD 위로 그려졌다.

정렬 순서는 프리팹에 자식 간 상대 오프셋만 굽고, 기준값은 런타임이 넣는다.

## 연출 파트 완료 체크리스트

- [ ] 미측정 항목 0 — 못 잰 것은 `미측정(사유)` 로 적고 재측정 대기에 등록했다
- [ ] 내 권한 밖 파일을 건드리지 않았다 (PD 「역할 기동 규약」 권한표)

1. 합성 모드를 그 캔버스 기준으로 확인했나 (다른 캔버스의 `lighter` 에 속지 않았나)
2. 렌더 컴포넌트 기본값이 원본과 같은가
3. 원본 겹 수와 자식 수를 맞췄나
4. `shadowBlur` 를 수식으로 굽고 이론식과 대조했나
5. `lineWidth` 를 절대 픽셀로 다루나
6. 얇은 띠 텍스처 해상도가 충분한가
7. `t`/`dt` 를 받는 원본 함수가 유니티에서 실제로 움직이나
8. 애니메이션 방향·속도·주기가 원본 값인가
9. 반투명이 겹치는 자리의 알파를 방향에 맞게 역산했나
10. 카메라 `depth` 순서가 의도대로인가
11. 굽는 쪽 상수와 고르는 쪽 상수가 같은가
12. 여러 페이즈 연출에 `EditorSetPhase` 진입점이 있고 페이즈마다 한 장씩 구웠나 (「정지 프리뷰로는 애니메이션 상태를 못 본다」)
