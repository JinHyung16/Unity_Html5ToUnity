# 연출 파트 — HTML5 → Unity 이관

상위: [PD](PD.md) (PD)

**담당** — 렌더 패리티 · 합성 모드 · 글로우 · 절차 이펙트 베이크 · 애니메이션 · 색공간.
**한 줄 원칙** — 원본은 캔버스 API로 그린다. **API 호출을 줄 단위로 옮기고, 눈대중 배율을 쓰지 않는다.**

**역할** — 나는 **지식 담당자**다. 이관에 직접 참여하지 않는다.
[Transfer_Artist](Transfer_Artist.md) 가 퀄리티까지 100% 이관할 수 있도록 **정확한 정보를 제공**하는 것이 산출물이다.
**정적 캡처에는 `animation` 과 `:hover` 가 안 찍힌다** — 원본을 돌려 보며 파악한다.

**역할 선언** — 이 역할로 들어갈 때 다음을 **출력한다** (PD 「역할 기동 규약」).

```
[역할 전환] 지금부터 나는 FX(지식 담당)다.
  할 수 있는 것 : 원본 읽기·실행 · 05_연출.md / 06_리소스.md 작성
  하지 않는 것  : 프리팹·아트 생성 (그건 Transfer_Artist 가 한다)
```

**이전 역할의 결론은 md 에 적힌 것만 인정한다.** 기억으로 이어가지 않는다.

## 착수하면 가장 먼저 하는 일 — 그리기 파라미터 전수표

코드를 고치기 전에 원본에서 **모든 그리기 파라미터를 뽑아 표로 만든다.**

```bash
grep -n "globalCompositeOperation" 원본.html    # 합성 모드 — 어느 캔버스인지까지 구분
grep -n "lineWidth" 원본.html                   # 선 굵기 (절대 픽셀이다)
grep -n "shadowBlur\|shadowColor" 원본.html      # 글로우
grep -n "globalAlpha" 원본.html                 # 알파
grep -n "createRadialGradient\|createLinearGradient" 원본.html
```

**[예시]** 한 프로젝트의 완성표 — 값은 그 원본의 실측이고, 라인은 grep 으로 재확정한다:

| 대상 | 원본 값 | 원본 라인 | 우리 값 | 상태 |
|---|---|---|---|---|
| 노바 링 | `lineWidth 4.5` · `shadowBlur 14` | 5231 | 4.5 + 소프트링 | ✓ |
| 오라 외곽선 | `lineWidth 1.5` | 5077 | 1.5 | ✓ |
| 궤도폭격 예고 | `lineWidth 3` · `shadowBlur 10` | 5229 | 3 + 소프트링 | ✓ |
| 아군 탄 | `shadowBlur 12`(크리 16) | 5691 | 동일 | ✓ |
| 적 탄 | `shadowBlur 9`(큰 탄 18) | 5761 | 동일 | ✓ |

**이 표의 빈 칸이 곧 남은 일이다.** 지적받은 것만 고치면 나머지는 계속 눈대중으로 남는다.

## 합성 모드 — 프로젝트 기본값이 원본과 반대일 수 있다

**원본이 무엇으로 합성하는지 먼저 확정한다.** 캔버스는 프레임 시작에 합성 모드를 정규화하는 경우가 많다.

```js
// 원본.html — 전투 그리기 진입 첫 줄 (라인은 grep 으로 재확정)
bx.globalCompositeOperation='source-over';   // 이후 끝까지 안 바꾼다
```

파일 전체에 `'lighter'` 가 여러 번 나오지만 **전부 다른 캔버스**(컷신·인트로용 `ctx`)였다.
**어느 컨텍스트에 거는지까지 봐야 한다.**

> **[사고]** 우리 도형 컴포넌트가 `_additive = true` 를 **기본값**으로 들고 있었다.
> 아무도 가산을 켜지 않았는데 탄환·드론·설치물·링·유닛 발광·보호막이 전부 가산이었다.
> 겹칠수록 흰색으로 타서 화면이 하얗게 뭉갰다.

**규칙**

- **원본에 없는 렌더 기능은 기본값도 꺼 둔다.** 「필요할 때 켜면 되지」가 아니라, 켜져 있으면 새어 나간다.
- 기능을 아예 안 쓰기로 했으면 **코드에서 지운다.** 스위치를 남기면 다음 사람이 켠다.
- 프리팹에 옛 머티리얼이 남아 있을 수 있으므로 **런타임에서 되돌리는 안전장치**를 둔다.
- 검증은 실측으로 — 활성 렌더러를 전수 세어 가산이 0인지 본다
  (**[예시]** `활성 SpriteRenderer 70개 → 전부 Sprite-Lit-Default (가산 0)`).

**발광은 가산으로 내는 게 아니다.** 원본은 `shadowBlur` 로 내고, 그건 아트에 이미 구워져 있다(「글로우」).

## 글로우 — `shadowBlur` 는 수식이 있다

캔버스 `shadowBlur = b` 는 도형의 알파를 **σ = b/2 가우시안으로 흐린 것**을 도형 **아래**에 깐다.

### 작은 도형은 봉우리 알파가 크게 내려간다

반지름 `r` 원판이면 중심 알파는 대략

```
peak ≈ 1 − exp(−(r/σ)²/2)
```

`r=7, σ=6` 이면 **0.49**다. 이 감쇠를 무시하고 상수 알파(예: 0.75)를 깔면
**모든 글로우가 두 배 밝은 발광 덩어리**가 된다.

### 눈대중 배율 대신 수치 적분해서 굽는다

원판을 가우시안으로 흐린 반경 프로파일을 **수치 적분**해 굽는다.
결과는 `k = σ / 도형반지름` 에만 의존하므로 **k 계열로 굽고 런타임이 가장 가까운 것을 고른다.**

```
텍스처 반경 = 도형반지름 × (1 + 3k)     // 가우시안 3σ 까지
알파는 프로파일이 들고 있으므로 런타임 tint 알파는 1
```

**반드시 이론식과 대조한다.** **[예시]** 실측 — 프로젝트마다 다시 잰다:

| k = σ/반지름 | 실측 peak | 이론 `1−exp(−(1/k)²/2)` |
|---|---|---|
| 0.35 | 0.984 | 0.983 |
| 0.50 | 0.863 | 0.865 |
| 0.70 | 0.639 | 0.640 |
| 1.00 | 0.392 | 0.393 |
| 1.40 | 0.224 | 0.225 |
| 2.00 | 0.118 | 0.118 |

소수 3자리까지 맞으면 그 베이크는 믿어도 된다. **「비슷해 보인다」로 끝내지 않는다.**

#### ⚠ 수식이 맞아도 **인자 단위**가 틀리면 전부 어긋난다

위 표는 σ 를 **직접** 넣어 검산한 것이다. 실제 호출부는 σ 가 아니라
원본 `shadowBlur` 를 넘기고 헬퍼가 `σ = blur/2` 로 바꾼다 — **여기서 단위가 갈린다.**

> **[사고]** 한 화면의 엔티티 십수 종이 전부 `shadowBlur / r * 2` 를 넘기고 있었다.
> 헬퍼가 다시 반으로 나누므로 **σ 가 정확히 두 배**가 됐다.
> 봉우리 감쇠 수식은 멀쩡했고 표와도 맞았다 — **코드만 봐서는 안 보인다.**
> 증상은 「탄환 글로우가 쨍하다」 하나뿐이었다.

**단위 규칙을 헬퍼 주석에 못박는다.** 생성기가 두 좌표계를 쓰는 일이 흔하다:

| 생성기 | 로컬 단위 | 넘기는 값 |
|---|---|---|
| 원본 픽셀 좌표 (장비 프롭) | 1 = 1 CSS px | `shadowBlur` **그대로** |
| 반지름 정규화 (엔티티 생성기) | 1 = 원본 `r` | `shadowBlur / r` |

**다른 보정은 없다.** `*2`·`/2` 가 붙어 있으면 그 자체가 신호다.

**판정은 구운 PNG 의 알파 프로파일로 한다** (UIUX 「절차 생성 도형은 구운 PNG의 알파를 직」).
σ 가 두 배면 이렇게 나온다 (**[예시]** 위 사고의 실측):

| 중심에서 | σ 두 배 (틀림) | σ 정상 |
|---|---|---|
| 1.0 r | 197 | **237** ← 본체가 진해진다 |
| 1.27 r (도형 끝) | 25 | **65** |
| 2.0 r | 6 | **0** ← 바깥이 깨끗해진다 |

σ 를 반으로 줄이면 **바깥 번짐이 사라지고 본체는 오히려 진해진다** —
`peak = 1 − exp(−(halfWidth/σ)²/2)` 가 같이 올라가기 때문이다.
「글로우를 줄였는데 총 알파가 늘었다」는 정상이고, 그게 원본의 「깔끔한 도형」이다.

### ★ 레이어 수를 센다 — 「글로우가 세다」의 진짜 원인은 대개 본체 누락

원본이 한 개체를 몇 겹으로 그리는지 세고, 우리 렌더러의 자식 수와 맞춘다.

```js
// 원본 아군 탄 (5691 — 라인은 grep 으로 재확정) — 세 겹이다
shadowColor=pcol; shadowBlur=_bl;                    // ① 글로우
fillStyle=pcol; ellipse(0,0,_pr2+3,_pr2-1); fill();  // ② 본체 타원
shadowBlur=0;
fillStyle='#eaffff'; arc(0,0,_pr2*0.5); fill();      // ③ 밝은 코어
```

> **[사고]** 우리는 ①③만 그렸다. 또렷한 알맹이가 없으니 **「글로우가 쓸데없이 세고 퀄이 낮다」**
> 로 보였다. 실제 원인은 글로우가 아니라 **②가 통째로 없는 것**이었다.

**증상과 원인이 어긋나는 대표 사례다.** 발광이 과해 보이면 글로우를 줄이기 전에 **레이어 수부터 센다.**

| 세는 법 | 명령 |
|---|---|
| 원본 | 그 draw 블록에서 `fill()` · `stroke()` · `drawImage(` 호출 수 |
| 우리 | 그 Visual 프리팹의 `SpriteRenderer` 자식 수 |

## 선 굵기는 **절대 픽셀**이다

원본 링·테두리는 전부 고정 픽셀 스트로크다. **반지름 비례로 구우면 큰 반지름에서만 틀어진다.**

> **[사고]** 링 텍스처를 「굵기 = 지름의 16%」로 구워 뒀다.
> 반지름 200짜리 오라가 **64px 두께**로 나왔다 (원본 1.5px — **40배**).
> 반지름이 작을 때는 그럴듯해서 초기 화면만 보면 안 드러난다.

**해결** — 「굵기 / 반지름」 비율 계열로 굽고 런타임이 **로그 스케일 최근접**으로 고른다.

```
ratios = { 0.006, 0.012, 0.024, 0.048, 0.096, 0.192, 0.384 }   // 등비 — [예시] 계열 값은 프로젝트가 정한다
고를 때: wanted = lineWidth / radius,  거리 = |log(ratio) − log(wanted)|
```

등비 계열은 **선형 거리로 고르면 큰 쪽에 쏠린다.** 반드시 로그 거리를 쓴다.

**[예시]** 한 프로젝트의 실측 결과 — 값은 프로젝트마다 다시 잰다:

| 용도 | R | 원본 굵기 | 실제 굵기 |
|---|---:|---:|---:|
| 오라 | 200 | 1.5 | 1.20px |
| 노바 초기 | 20 | 4.5 | 3.84px |
| 노바 중반 | 100 | 4.5 | 4.80px |
| 궤도폭격 | 135 | 3.0 | 3.24px |

**해상도도 같이 올린다.** 128px 텍스처를 400px로 늘리면 「픽셀이 깨져 보인다」는 말이 나온다.
얇은 띠를 담는 텍스처는 512 이상으로 굽는다.

**`shadowBlur` 가 붙은 스트로크는 두 겹이다** — 넓은 소프트 링을 아래에, 또렷한 선을 위에.
(원본은 `stroke()` 한 번에 둘 다 나온다)

## 절차 이펙트는 재구현하지 말고 원본에서 베이크한다

**[예시]** 원본 3프레임을 드로우 명령 스트림으로 추출해 실측한 결과:
**손으로 다시 그리면 최대 Δ183, 원본 렌더 결과를 추출해 구우면 Δ0.**

- 원본 드로잉 코드를 **줄 단위로** 옮긴다. 캔버스 API를 그대로 받는 2D 페인터를 쓴다
  (`FillRoundRect` · `StrokePolyline` · `Paint.LinearY/Radial` · `Halo`(=`shadowBlur`) 등).
- **색이 데이터로 갈리는 것만 흰색+알파로 굽는다.** 나머지는 색까지 구워야 원본과 같은 그림이 나온다.
- 원본이 다른 폰트·SVG를 쓰는 것도 **그 원본을 렌더해서** 가져온다. 손으로 다시 그리지 않는다.
  (**[예시]** 아이콘 92종은 브라우저에서 원본 SVG를 그대로 렌더해 아틀라스로 뽑았다)

**베이크 계열은 「굽는 쪽 상수」와 「고르는 쪽 상수」가 두 파일에 나뉜다.**
둘이 어긋나면 크기가 조용히 틀어진다 — 서로를 주석으로 가리키고, 값이 바뀌면 같이 바꾼다.

## 애니메이션 — 정적 PNG로는 연출이 사라진다

**원본 함수 인자에 `t` 나 `dt` 가 있으면 반드시 움직이는 것이다.**

| 원본 형태 | 옮기는 법 |
|---|---|
| `0.5 + 0.5·sin(t·ω)` 맥동 | **같은 그림을 두 번 굽는다** — 골(pulse=0)과 마루(pulse=1). 마루를 위에 얹고 알파를 0→1 흔들면 맥동 요소만 오가고 나머지는 픽셀 동일이라 안 변한다. 주기 = `2π/ω` |
| `rotate(t·ω)` 등속 회전 | 회전 요소만 따로 굽고 회전 컴포넌트 |
| `rotate(sin(t·ω)·A)` 왕복 | 별도 레이어 + 사인 회전 컴포넌트 |
| `(t·k) % m` 스캔선·타일 | 별도 레이어 + 드리프트 컴포넌트 |

**크로스페이드 기법이 핵심이다.** 맥동은 대부분 이걸로 끝나고, 회전·이동만 별도 레이어가 필요하다.
범용 트윈 라이브러리를 새로 짜지 않는다 — 최소 컴포넌트를 하나씩 만든다.
**UI 버튼의 배율 움직임(펄스·호버·상태)은 이미 최소 세트가 있다** — [UIFramework](UIFramework.md) 「UI 연출」. 그림을 굽는 것이 아니라 배율을 곱하는 것이라 크로스페이드가 아니다.

**방향·속도를 원본에서 확인한다.** **[사고]** 배경 드리프트를 `11px/s` 로 넣었는데 원본은 **1.1**px/s 였다.
타일링 방향(아래로 흐르는지), 순환 폭(이미지 높이), 왕복 여부까지 원본을 본다.

### ★ 정지 프리뷰로는 애니메이션 상태를 못 본다 — **페이즈 강제 진입 훅을 표준으로 둔다**

프리뷰 하네스는 창을 한 프레임만 굽는다. 그래서 **여러 페이즈를 거치는 연출**은
「첫 프레임이 맞다」까지만 증명되고 나머지는 통째로 미검증으로 남는다.

> **[사고]** 10연 뽑기 그리드가 **카드가 뒤집히지 않는** 상태였다.
> 정지 캡처는 뒤집기 전 상태가 정답이라 **몇 턴째 정상으로 보였다.**
> 「연출이 밋밋하다」는 지적을 받고서야 찾았다.

**연출을 붙일 때 페이즈 진입점을 같이 만든다.** 나중에 붙이면 안 붙인다.

```csharp
#if UNITY_EDITOR
/// <summary>프리뷰·검수용 — 페이즈를 건너뛰고 그 상태로 바로 앉힌다. 트윈은 끝난 값으로 확정한다</summary>
public void EditorSetPhase(Phase phase) { ... }
#endif
```

**요건 3가지**
1. **모든 페이즈에 이름이 있다.** 「연출 중」 같은 뭉뚱그린 상태 하나면 진입점을 못 만든다.
2. **진입 시 트윈을 끝난 값으로 확정한다.** 중간값이면 캡처가 매번 달라져 대조가 안 된다.
3. **프리뷰가 페이즈마다 한 장씩 굽는다.** 원본 캡처도 같은 페이즈로 찍어 짝을 만든다
   (`capture_*.js` 에 단계별 캡처를 붙인다).

## 색공간 — 프로젝트당 한 번 결정하고 그에 맞춰 전부 짠다

**캔버스는 감마(sRGB) 공간에서 합성한다.** 유니티가 Linear면 같은 색·같은 알파라도 결과가 다르다.

**[예시]** 한 프로젝트의 실측 — 색·알파가 다르면 값도 다르다:

| 케이스 | 캔버스 | Gamma 예측 | Linear 예측 |
|---|---|---|---|
| 가산 (시안+적 · 각 α0.5) | R 156 | 155.5 (Δ0.5) | 190.8 (**Δ34.8**) |
| 알파 합성 (남색 + 앰버 α0.6) | R 157 | 157.0 (Δ0) | 203.6 (**Δ46.6**) |

- **원인은 합성 수식이다.** `src·a + dst·(1−a)` 를 리니어 값으로 계산하면 감마보다 밝다.
  **불투명 단일 레이어는 왕복이 맞아떨어져 문제가 없다** — 반투명이 겹칠 때만 뜬다.
- 「Vertex Color Always In Gamma」 류 옵션과는 **무관하다.** 그건 버텍스 컬러 인코딩 문제고
  블렌딩 수식은 안 바뀐다. (**[예시]** 이 저장소 기준 — Unity 6000.3 + URP 에는 그 설정 자체가 없다)

**Linear로 확정된 프로젝트에서는 알파를 역산한다.**
어두운 배경 위에서 감마 알파 `a` 와 같게 보이려면 **`a^2.2`** 를 넣는다.
베이크 스프라이트는 굽는 마지막에 알파만 바꾸면 된다 — `a=1` 은 안 변해 실루엣이 보존된다.

**어디가 뜨는지는 픽셀로 특정한다.** **[예시]** 한 프로젝트의 실측:

| 지점 | 원본 | 유니티 |
|---|---|---|
| 상단바 배경 | (13,20,33) | (10,18,32) ✓ |
| 최하단 배경 | (16,26,42) | (15,29,46) ✓ |
| **배경 연출 영역** | **(1,10,11)** | **(14,22,34)** ✗ |

UI 판은 이미 맞고, 뜨는 건 **반투명이 여러 겹 쌓이는 자리**뿐이다. 거기만 고친다.

색·알파는 원본 `:root` 변수에서 가져오고 하드코딩하지 않는다.
반투명 선·딤은 역산값을 쓴다 (**[예시]** CSS .5 → 대략 .22~.3).

## 카메라 · 정렬

**카메라 depth가 같으면 렌더 순서가 비결정적이다.**

> **[사고]** 월드 카메라와 UI 카메라가 **둘 다 depth −1** 이었다.
> 월드 오브젝트가 상단 HUD 위로 그려졌다.

월드 스프라이트의 `sortingOrder` 를 아무리 만져도 **카메라가 다르면 소용없다** —
카메라 간 순서는 `depth` 가 정한다. UI가 월드 위로 안 올라오면 여기부터 본다.

**정렬 순서는 프리팹에 자식 간 상대 오프셋만 굽는다.** 기준값은 런타임이 넣는다.

## 연출 파트 완료 체크리스트

- [ ] **미측정 항목 0** — 못 잰 것은 `미측정(사유)` 로 적고 **재측정 대기**에 등록했다
- [ ] **내 권한 밖 파일을 건드리지 않았다** (PD 「역할 기동 규약」 권한표)

1. 원본의 **합성 모드**를 그 캔버스 기준으로 확인했나 (다른 캔버스의 `lighter` 에 속지 않았나)
2. 우리 렌더 컴포넌트의 **기본값**이 원본과 같은가
3. 원본이 한 개체를 **몇 겹**으로 그리는지 세고 자식 수를 맞췄나
4. `shadowBlur` 를 수식으로 굽고 **이론식과 대조**했나
5. `lineWidth` 를 **절대 픽셀**로 다루나 (반지름 비례로 굽지 않았나)
6. 얇은 띠 텍스처의 해상도가 충분한가 (늘렸을 때 안 깨지나)
7. 원본에서 `t`/`dt` 를 받는 함수가 유니티에서 실제로 움직이나
8. 애니메이션 **방향·속도·주기**가 원본 값인가
9. 반투명이 겹치는 자리의 알파를 역산했나
10. 카메라 `depth` 순서가 의도대로인가
11. 굽는 쪽 상수와 고르는 쪽 상수가 같은 값인가
12. 여러 페이즈를 거치는 연출에 **`EditorSetPhase` 진입점**이 있고, 페이즈마다 한 장씩 구웠나 (「정지 프리뷰로는 애니메이션 상태를 못 본다」)
