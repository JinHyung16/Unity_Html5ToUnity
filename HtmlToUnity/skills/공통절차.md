# 공통 절차 — **전 파트가 매번 쓰는 것**

상위: [PD](PD.md) (PD)

**이 문서는 역할이 없다.** 지식·이관·PD 누구든 **재거나 원본을 뒤질 때 연다.**
PD 안에 있으면 UI 담당자가 A/B 측정법 하나 보려고 오케스트레이터 문서를 통째로 열게 되므로 따로 뒀다.

**언제 여나** — 측정·캡처·감사·컴파일 판정을 할 때, 그리고 **원본에서 사양을 캐낼 때.**
사고 사례와 막는 장치는 [재발방지](재발방지.md) 에 있다.

---


## 검수 절차 — 재기 전에 상태부터 맞춘다

### ⚠ 세이브를 먼저 백업한다

**Play Mode 중 자동 저장이 돈다.** 상태를 조작하면 사용자의 실제 세이브가 덮인다.
백업 → 측정 → **반드시 복원**. (실제로 덮인 사고가 있다)

### ⚠ 원본을 재기 전에 — **폰트가 뜬 뒤에 잰다**

원본이 웹폰트(Google Fonts 등)를 쓰면 **첫 페인트는 폴백 폰트로 그려진다.**
그 상태에서 잰 크기는 **다른 폰트의 값**이다. 글자가 폭·높이를 정하는 요소
(`width:auto` 컨테이너 · 버튼 · 라벨)는 **로드 전후가 다르다.**

```js
await document.fonts.ready;          // ← 이 줄 없이 잰 값은 사양이 아니다
el.getBoundingClientRect();
```

**두 번 재서 같은지 본다.** 다르면 나중 값이 사양이고, **먼저 잰 값은 오염이므로 원장에 적는다**
(분석로직 「오염된 내용」). → `재발방지.md` #1

### ⚠ 「그 기능이 없다」는 **정확한 패턴으로** 증명한다

부재 증명은 존재 증명보다 위험하다. **틀리면 없는 기능을 만들거나 있는 기능을 빠뜨린다.**
부분 일치 grep 은 조용히 거짓 양성을 낸다.

```bash
grep -c "play" 원본.js                       # ✗ display · scoreDisplay 가 걸린다
grep -nE "new Audio|<audio|\.play\(\)" 원본.js   # ✓ 경계가 있는 패턴 + 줄을 눈으로 본다
```

**개수만 보지 말고 매칭된 줄을 출력해 확인한다.** → `재발방지.md` #2

### ★ A/B 측정 — 상태를 맞추고 개체를 센다

**스크린샷을 믿지 마라.** 캔버스 게임은 픽셀로 셀 수 없는 게 대부분이고,
캡처 상태와 유니티 상태가 다르면 뭐가 결함인지 구분조차 안 된다.

**① 상태를 먼저 맞춘다.** 캡처는 전부 특정 세이브 상태의 스냅샷이다.
신규 계정 유니티와 풀해금 캡처를 비교하면 「적이 없다·드론이 없다」가 전부 결함으로 보이지만 전부 정상이다.

원본의 치트/디버그 명령을 그대로 이식해 **같은 한 줄로 양쪽을 같은 상태로 올린다.**
치트 한 줄로 양쪽을 같은 상태에 올려 두고, **그 상태를 기준 캡처의 상태로 못박는다.**

**입력을 끝까지 맞춘다.** 스킬만 맞추고 유닛·등급·장비·동료가 다르면 계산이 수십 % 어긋난다.

**상태 정합 체크리스트 — 하나라도 다르면 그 구간 점수는 의미가 없다.**

| 맞출 것 | 안 맞추면 |
|---|---|
| 진행도 (스킬·유닛·등급·장비·동료) | 계산이 수십 %까지 어긋난다 |
| **보유 재화** | 자릿수가 달라 상단바 구간이 통째로 깎인다 |
| 스크롤 위치 · 선택 대상 · 활성 탭 | 아예 다른 화면을 비교하게 된다 |
| **배경이 영상인가** | 프레임이 달라 그 구간은 40~60%가 정상이다 |

> **[사고]** 한 화면의 구간 점수가 40~60%로 나와 결함으로 보고할 뻔했다.
> 원인은 **배경 영상 프레임 차이 + 재화 보유량 차이**였고, 결함이 아니었다.
> **점수가 낮으면 결함을 찾기 전에 이 표부터 채운다.**

**② 픽셀이 아니라 개체를 센다.** 원본은 JS로 전역 상태를 직접 읽고,
유니티는 리플렉션으로 private 리스트를 읽는다. **같은 항목을 같은 이름으로** 센다.
**종류 분포까지 센다** — 총량이 비슷해도 `Elite:5` 가 살아 있으면 뭔가 안 죽고 있는 것이다.

**③ 판정 표를 만든다.** 실시간 시뮬은 흔들리므로 2~3회 샘플링해 **같은 대**인지를 본다.

**[예시]** — 표의 모양이다. 값은 그 프로젝트에서 샘플링한 실측으로 채운다:

| 항목 | 원본 | 고치기 전 | 고친 후 |
|---|---|---|---|
| 살아있는 적 | 1 / 6 / 2 | 11 / 28 | 2~4 ✓ |
| 아군 탄 | 108 / 111 / 97 | 35 / 4 | 111 ✓ |
| 적 탄 | 0 | 7 / 12 | 0 ✓ |

### ★★ 재기 전에 **노이즈가 0인 기저 상태**를 만든다

「상태를 맞춘다」의 한 걸음 더다. 상태를 맞춰도 **재려는 것 말고 다른 것이 움직이면**
델타에 그게 섞인다. 특히 원본에 **무작위·자동 진행**이 있으면 그렇다.

> **재려는 변화 외의 변화가 0인 판**을 먼저 설계한다. 그게 없으면 벡터가 회차마다 흔들린다.

| 원본에 있는 것 | 노이즈 | 기저 상태 설계 |
|---|---|---|
| 자동 매치·자동 전투 | 재는 동안 점수·개체가 계속 변한다 | **매치·전투가 원천적으로 불가능한 배치**를 만든다 |
| 무작위 생성 | 잰 값이 회차마다 다르다 | 생성이 안 일어나는 상태로 두거나, **생성 자리를 대조에서 제외**한다 |
| 타이머 | 시간이 값을 바꾼다 | 타이머가 없는 모드로 재거나 정지 상태에서 잰다 |

**기저 상태가 유효한지 먼저 증명한다.** 깔고 방치했을 때 **변화가 0** 이어야 한다 —
그 0이 「하네스가 노이즈를 안 만든다」는 증거다. 이 확인 없이 잰 값은 근거가 없다.

> **[예시]** 값이 `(열 + 2×행) % 3` 인 판은 가로·세로 인접이 절대 같아지지 않아
> 자동 매치가 원천 불가능하다. 깔고 방치하면 점수 증가가 0이고, 그 위에 **원본이 안 쓰는 값**을
> 심으면 잰 델타가 심은 것에서만 나왔다고 말할 수 있다.

**대조에서 제외할 자리를 미리 적는다.** 무작위가 개입하는 칸은 벡터에 `RANDOM` 으로 표시하고
유니티 대조에서 빼면 된다 — **제외한다고 적지 않으면 다음 회차에 「값이 틀렸다」로 읽힌다.**

### ⚠ 하네스에 `requestAnimationFrame` 을 쓰지 않는다

**브라우저 창·패널이 화면에 안 보이면 `requestAnimationFrame` 이 멈춘다.**
합성(compositing)이 안 돌기 때문이다. rAF 로 폴링하는 하네스는 **통째로 정지**하고,
겉으로는 「원본이 안 돈다」처럼 보인다.

**`setInterval`·`setTimeout` 은 계속 돈다.** 그래서 폴링은 타이머로 한다.

```js
// ✗ 패널이 숨겨지면 여기서 멈춘다
await new Promise(r => requestAnimationFrame(r));

// ✓ 숨겨져 있어도 돈다
await new Promise(r => setTimeout(r, 10));
```

> **[사고]** rAF 폴링으로 벡터 9개를 재는 하네스가 **30초 타임아웃으로 죽었다.**
> `document.hidden` 이 `true` 였고, 같은 조건에서 타이머로 바꾸자 **원본 틱이 59ms 만에** 잡혔다.
> 원본은 멀쩡히 돌고 있었고 **하네스만 멈춰 있었다.**

**막힌 것 같으면 `document.hidden` 을 먼저 찍어 본다.** 그리고 **원본이 정말 멈췄는지**를
타이머 한 번으로 확인한다 — 하네스와 원본을 구분하지 못하면 없는 결함을 쫓게 된다.

### 교전 중 프레임을 얼려서 본다 (게임 코드 무수정)

전투가 40초 만에 끝나는데 도구 왕복이 10~30초라, 프로브를 보내면 이미 결과창이다.
**에디터 쪽 `EditorApplication.update` 훅**으로 원하는 조건에서 얼린다.

```csharp
EditorApplication.CallbackFunction hook = null;
hook = () => {
  var ctx = GameManager.Instance?.Combat?.Context;
  if (ctx == null || GameManager.Instance.Combat.IsRunning == false) return;
  ctx.Player.Hp = ctx.Player.MaxHp;        // 조사 중 격침 방지
  if (/* 보고 싶은 조건 */) {
    EditorApplication.isPaused = true;
    EditorApplication.update -= hook;      // 한 번만 잡고 스스로 제거
  }
};
EditorApplication.update += hook;
```

- **`Time.timeScale` 을 낮추는 건 안 통한다** — 그 상태에선 출격 전이 자체가 안 걸린다.
- **일시정지는 풀려 버린다** — 원격 도구가 에디터를 틱시키기 때문이다.
  조사 결과는 **파일로 덤프**하는 편이 안정적이다.
- **모달을 띄워 시뮬을 얼리는 게 가장 쉽다.** 원본에 「선택창이 뜨면 시뮬 정지」 규칙이 있으면
  그 창을 띄운 상태가 곧 정지 프레임이다 — 캡처·측정 모두 여기서 한다.

### ★★ 원본을 «결정적으로» 찍는 법 — G4 대조의 정본을 만든다

렌더 대조는 **두 그림이 같은 상태일 때만** 뜻이 있다.
원본을 그냥 찍으면 무작위·자동 진행·폰트 로드 때문에 **찍을 때마다 다른 그림**이 나온다.

| 조건 | 왜 |
|---|---|
| **난수를 시드로 고정** | 원본의 난수 함수 자리에 시드 LCG 를 끼운다. 판이 매번 같아진다 |
| **주기 진행을 막는다** | 원본의 주기 호출을 빈 함수로 덮는다. **찍는 순간에 판이 안 바뀐다** |
| **원격 리소스를 로컬로** | 네트워크에 기대면 재현이 안 되고 느리다. 같은 파일을 받아 로컬 경로로 바꾼다 |
| **웹폰트를 뺀다** | 글자는 대조에서 빼는 항목이다. 폰트 로드 타이밍이 그림을 흔들 이유가 없다 |
| **레이아웃 크기를 못 박는다** | 아래 |

⚠ **원본은 «복사본»에 손댄다.** 원본 폴더의 파일은 건드리지 않는다.

#### ⚠ `file://` 은 «정적 스냅샷»이 될 수 있다

브라우저 패널이 프로젝트 밖 파일을 열면 **스크립트가 돌지 않는 스냅샷**으로 바꿔 놓기도 한다.
그러면 게임이 시작조차 안 되는데 **화면은 멀쩡히 보인다** — 「원본이 원래 이런가」로 오해한다.
**로컬 HTTP 서버로 연다.**

#### ⚠ 「좌표를 재는 실행」과 「그림을 찍는 실행」의 배치가 다를 수 있다

헤드리스 브라우저는 **좌표를 재는 실행과 그림을 찍는 실행에서 보이는 창 크기가 다를 수 있다**
(스크롤바·페이지 높이 때문). 그러면 잰 좌표로 자른 조각이 **엉뚱한 자리**가 된다 — 실측으로 확인했다.

> **대책** — 캡처용 페이지에 **레이아웃 크기를 픽셀로 못 박는다**
> (`html, body { width: …px; height: …px; overflow: hidden; }`).
> 그러면 창 크기와 무관하게 두 실행의 배치가 같아진다.

좌표는 **DOM 안에 심어서** 꺼낸다 — 잰 값을 숨은 요소의 텍스트로 넣고 DOM 을 덤프한다.

### ★ 요소 대조는 «요소가 실제로 칠하는 자리»만 센다

원본과 우리는 **배경이 다르게 놓인다** (원본은 흐름 배치, 우리는 목표 화면비 재배치).
그래서 요소를 통째로 겹쳐 세면 **투명한 자리로 새어든 배경**이 점수를 먹는다.

> **[사고]** 사탕 6종이 19~39% 로 나와 「그림이 다르다」로 읽었다.
> 원인은 ① 반투명 판이 불투명하게 구워진 것 ② **가장자리로 새어든 서로 다른 배경**이었다.
> ①을 고치고 ②를 마스크로 걷어내니 **99.7~100%** 였다.

| 요소 종류 | 재는 법 |
|---|---|
| 불투명한 그림 (스프라이트) | 원본 알파에서 **심(心)만** 남긴 마스크로 센다. 가장자리 몇 px 는 깎는다 |
| **반투명한 면** | 절대색으로 못 잰다 — 뒤에 뭐가 있냐에 달렸다. **뒷배경이 같은 색인 자리**를 골라 앞색을 대조하거나 «실효 알파»를 역산한다 |
| 모서리·모양 | 색이 아니라 **반지름**을 잰다 |
| 크기가 「의도된 차이」인 요소 | **색만** 본다. 크기 차이는 확정표 등재로 갈음한다 |

⚠ **자산과 화면을 갈라서 본다.** 「화면이 다르다」의 원인이 자산일 수도, 렌더일 수도 있다.
**자산끼리 먼저 대조**하면 (원본 PNG vs 우리 PNG) 어느 쪽 문제인지 한 번에 갈린다.

### 화면 캡처는 비동기다

`ScreenCapture.CaptureScreenshot` 은 **프레임 끝에 기록된다.** 같은 호출 안에서 파일을 읽으면 없다.
그리고 그 사이에 **Play Mode가 리셋될 수 있다** — 캡처 요청과 파일 확인 사이에 게임이
초기 화면으로 돌아가 엉뚱한 화면이 찍히는 일이 실제로 두 번 있었다.
**모달로 시뮬을 얼린 뒤 찍는다**(4-2b).

### 캡처는 어디에 쌓나 — `Html_Screenshot/`

원본을 돌려 보며 찍은 캡처를 세션마다 흘려보내면 **다음 회차가 같은 것을 다시 찍는다.**
**원본 폴더 최상위 아래**, `HtmlToUnityLogic/` 과 같은 층에 쌓는다 — **없으면 만든다.**

```
<원본 HTML5 폴더>/
├─ HtmlToUnityLogic/
└─ Html_Screenshot/
    ├─ _대장.md          ← 이게 본체다. PNG 는 첨부물이다
    └─ <파일명>.png
```

**Assets 안이 아니다.** 원본 옆이라야 원본과 같이 갱신되고 유니티 임포트에 안 섞인다.

> ★ **이 폴더는 증거지 사양이 아니다.** 여기서도 판정은 **①원본 코드 → ②규약 문서 → ③캡처** 순이다
> (「점수를 믿기 전에」). 잘 정리된 캡처 폴더는 **캡처를 1순위처럼 보이게 만든다** —
> 오염 1갈래 「캡처를 사양으로 삼음」이 나는 자리가 정확히 여기다.

#### `_대장.md` 없이 PNG 만 쌓지 않는다

**상태가 안 적힌 캡처는 A/B 에 못 쓴다** (「A/B 측정」 상태 정합 체크리스트).
못 쓰는 파일이 쌓이면 다음 회차는 그걸 근거로 쓰거나 다시 찍는다. 둘 다 손해다.

| 컬럼 | 무엇 | 비면 |
|---|---|---|
| 파일명 | 공백·복사본 접미 금지 (「이름 1.png」는 조용한 시한폭탄이다) | 주소가 깨진다 |
| 화면 | 원본의 어느 화면인가 | 어느 화면인지 모를 캡처가 된다 |
| **상태** | 진행도 · 보유 재화 · 선택 대상 · 활성 탭 | **A/B 불가.** 「상태 미기록」으로 적고 재촬영 대상에 남긴다 |
| 애니메이션 | 정지·끝 상태를 강제했나 | 한 프레임을 정색으로 오인한다 (오염 3갈래) |
| 근거 | 이 화면을 그리는 **원본 코드 위치** | 캡처가 유일 근거가 된다 = 오염 |
| 회차 | 언제 찍었나 | 어느 빌드의 캡처인지 모른다 |

**애니메이션이 붙은 화면은 끝 상태를 강제하고 찍는다.** t=0 이 찍히면 「기능이 없다」로 오판한다.

**커밋 여부는 프로젝트가 정한다.** PNG 는 diff 가 안 되므로, 커밋한다면 `_대장.md` 가
어느 회차의 캡처인지를 반드시 갖고 있어야 한다.

### ★ 에셋 등록은 **양방향**으로 감사한다

번들 시스템(Addressables 등)의 동기화 도구는 보통 **「파일 → 주소」 한 방향만** 보장한다.
반대 방향 — **코드·데이터가 요구하는 주소가 실제로 있는가** — 는 아무도 안 본다.
그래서 게임을 켤 때까지 모른다.

> ⚠ **사고 1** — 영상 파일이 언젠가 `Intro_start 1.mp4` 로 이름이 바뀌어 있었다(복사본 접미).
> 주소가 `art_video_intro_start 1` 이 되어 코드가 찾는 `art_video_intro_start` 와 어긋났고,
> 시작 화면 시네마틱이 `InvalidKeyException` 으로 죽었다. 동기화 도구는 「제거 0 · 건너뜀 0」 이라고 보고했다 —
> 도구 입장에선 아무 문제가 없었다.
>
> ⚠ **사고 2** — 새로 구운 텍스처를 등록하지 않아 런타임에서 통째로 못 읽었다.
> **파일을 만드는 생성기가 등록까지 책임지게** 고쳤다.

**감사 3종 (도구로 만들어 두고 화면 완료 전에 돌린다)**

| 항목 | 잡는 것 |
|---|---|
| 코드에 박힌 주소 리터럴 전수 → 등록 여부 | 이름이 어긋난 것 |
| 아트 파일명에 **공백·복사본 접미** | 주소를 깨뜨리는 파일명. 「이름 1.png」 는 조용한 시한폭탄이다 |
| 등록됐는데 파일이 없는 **고아** | 지운 뒤 남은 것 |

주의 — 감사기는 **폴더 엔트리**와 **폴더 접두어**를 오탐한다.
데이터의 아트 경로 중에는 파일이 아니라 폴더인 것이 섞여 있다(**[예시]** `Enemies/normal` 같은 카테고리 폴더 — 폴더면 실제 장수를 세어 대조한다).
파일 존재 검사에 디렉터리 예외를 넣고, 폴더 접두어는 Play Mode 로딩으로 확인한다.

### ★ 에디터를 못 돌려도 **컴파일 판정은 된다**

**유니티가 만든 `.csproj` 는 방금 추가한 파일을 모른다.** 에디터가 포커스를 받아야 다시 쓰기 때문이다.
그래서 `dotnet build Assembly-CSharp.csproj` 가 **새 파일을 빼고 통과**해 버린다 —
「0 에러」가 거짓이 되는 자리다.

**에디터 제어가 없으면 임시 프로젝트를 세워 직접 컴파일한다.** 유니티가 필요 없다.

```xml
<!-- [예시] 스크래치패드에 둔다. 프로젝트 안에 만들지 않는다 -->
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>netstandard2.1</TargetFramework>
    <EnableDefaultCompileItems>false</EnableDefaultCompileItems>
  </PropertyGroup>
  <ItemGroup>
    <Compile Include="<프로젝트>\Assets\Scripts\**\*.cs" />
  </ItemGroup>
  <ItemGroup>
    <Reference Include="UnityEngine.CoreModule">
      <HintPath><Unity설치경로>\Editor\Data\Managed\UnityEngine\UnityEngine.CoreModule.dll</HintPath>
      <Private>false</Private>
    </Reference>
  </ItemGroup>
</Project>
```

| 무엇을 잡나 | 무엇은 못 잡나 |
|---|---|
| 문법 · 타입 · 누락된 `using` · 시그니처 불일치 | **에디터 전용 API** (`UnityEditor.*`) — 참조를 따로 걸어야 한다 |
| 새로 추가한 파일 전부 | 패키지 의존 코드 — 그 DLL 을 참조에 추가해야 한다 |
| 어셈블리 분리와 무관하게 전수 | 프리팹·에셋 참조 무결성 (그건 에디터가 봐야 한다) |

⚠ **이 임시 프로젝트는 스크래치패드에 둔다.** 유니티 프로젝트 안에 만들면
`.csproj` 가 임포트에 섞이고 커밋 여부가 헷갈린다 (PD 「검증 산출물은 유니티 프로젝트 밖에 둔다」).

### ★★ 에디터가 열려 있으면 — **끄지 말고 «다리»로 시킨다**

배치모드가 필요한 유일한 이유는 «같은 프로젝트를 두 인스턴스가 못 연다»는 것이다.
그렇다면 두 번째 인스턴스를 띄우는 대신 **열려 있는 에디터에게 직접 시키면 된다** —
검사 한 번마다 에디터를 껐다 켜는 과정(1~3분 + 사람 화면이 사라짐)이 통째로 사라진다.

**다리의 모양** — 에디터 안에 «지켜보는 스크립트» 하나를 상주시킨다.

| 단계 | 하는 일 | 왜 |
|---|---|---|
| 1 | 셸이 요청 파일을 쓴다 (`{"id":…, "method":…}`) | 파일이 가장 단순한 IPC 다 |
| 2 | 에디터가 틱마다 보다가 **에셋을 새로고침**한다 | 밖에서 고친 스크립트를 먹어야 한다 — 포커스 없인 자동 새로고침이 안 온다 |
| 3 | **컴파일·임포트가 끝날 때까지** 기다린다 | 도메인 리로드가 나도 요청 «파일»이 남아 있어 리로드 뒤 이어받는다 |
| 4 | 메서드를 실행하고 **콘솔 로그를 잡아** 응답 파일로 쓴다 | 판정은 로그가 전부다 |

⚠ **요청·응답 파일은 `Temp/` 에 두지 않는다** — 유니티가 시작할 때 비운다 (재발방지 #38).

⚠ **재생(Play) 검사는 조심한다.** 배치용 재생 검사기는 끝에서 `EditorApplication.Exit` 를
부른다 — 다리로 돌리면 **사람이 쓰던 에디터가 꺼진다.** 다리로 돌리려면 검사기가
「다리가 시킨 실행인가」 플래그를 보고 **`ExitPlaymode`** 로 끝내야 한다.
그 전까지 재생 검사는 배치모드로 남긴다.

⚠ **첫 활성화만 재시작이 필요하다** — 다리 스크립트 자체가 컴파일되기 전에는
아무도 요청을 안 본다. 이후로는 재시작이 없다.

### ★★ 에디터 툴은 **배치모드로 직접 실행한다** — 사람에게 메뉴를 누르라고 하지 않는다

대화형 에디터 제어(MCP 등)가 없어도 **에디터 코드는 돌릴 수 있다.**
사람에게 「메뉴를 눌러 주세요」라고 하는 것은 **절차가 아니라 실패다**
(SKILL.md 「세 번째 목적이 나머지 둘의 완료 기준을 바꾼다」).

```bash
# [예시] 인자 없는 static 메서드를 헤드리스로 실행하고 로그를 파일로 받는다
<Unity실행파일> -batchmode -quit -nographics -silent-crashes \
  -projectPath <프로젝트> -executeMethod <Namespace.Class.Method> -logFile <로그>
```

**순서 — 닫고 · 돌리고 · 연다**

| # | 하는 일 | 왜 |
|---|---|---|
| 1 | 에디터 프로세스가 살아 있는지 본다 | 같은 프로젝트를 두 인스턴스가 못 연다 |
| 2 | 살아 있으면 **저장 안 된 작업이 날아갈 수 있다고 알리고** 승인을 받는다 | 사람의 작업을 임의로 버리지 않는다 |
| 2-b | **「⏳ 유니티를 재부팅 중입니다. 기다려주세요.」를 남긴다** | 아래 |
| 3 | 정상 종료를 요청하고 **프로세스가 실제로 사라질 때까지 기다린다** | 저장 확인 대화상자가 떠서 안 닫힐 수 있다 |
| 4 | **잔재 락파일**이 남았으면 지운다 | 프로세스가 없는데 락만 남는 경우가 있다 |
| 5 | 배치모드 실행 · **로그를 파일로 받는다** | 콘솔이 없으므로 로그가 유일한 결과다 |
| 6 | **다시 연다** — 열기 전에도 같은 문구를 남긴다 | 닫은 상태로 두지 않는다 |

#### ★ 재부팅 문구를 **빠뜨리지 않는다**

**사람은 화면이 사라진 것만 본다.** 유니티가 닫히고 몇 분간 아무 말이 없으면
「멈췄나」·「죽었나」로 읽힌다 — **기다리면 되는 상황인지 아닌지를 알 방법이 없다.**

> ⏳ **유니티를 재부팅 중입니다. 기다려주세요.**

| 언제 | 무엇 |
|---|---|
| 닫기 전 | 위 문구 + **저장 안 된 작업이 사라진다**는 경고 |
| 다시 열 때 | 위 문구 |
| 여러 단계를 이어 돌릴 때 | **마지막 단계에서만 연다** — 중간에 열면 다음 단계가 락에 막힌다 |

**러너가 대신 찍게 만든다.** 사람이 기억해서 찍는 문구는 바쁠 때 빠진다 —
닫는 경로와 여는 경로에 **문구를 박아** 두면 빠질 수 없다.

⚠ **종료 코드만 보고 성공으로 읽지 않는다.** 배치모드는 컴파일 에러가 나도
상황에 따라 0을 반환한다. **로그에서 `error CS` · `Exception` · 우리가 찍은 성공 문구**를
같이 확인한다.

⚠ **배치모드는 임포트를 동반해 느리다.** 백그라운드로 돌리고 로그를 읽는다 —
앞단에서 기다리면 세션이 멈춘다.

#### ⚠ 배치 로그는 **다음 실행이 지운다**

에디터는 시작할 때 임시 폴더를 비운다. 배치 로그를 거기 두면
**다음 배치가 앞 로그를 지운다** — 여러 단계를 잇달아 돌리면
**중간 단계의 로그가 통째로 사라진다.**

| 대응 | 내용 |
|---|---|
| **실행 직후에 읽는다** | 파이프라인이 각 단계 출력을 **그 자리에서** 갈무리하게 만든다 |
| 임시 폴더 밖에 쓴다 | 여러 단계를 돌릴 거면 로그를 지워지지 않는 자리에 둔다 |

#### ⚠ 「성공 표시」와 「실패 표시」의 모양이 다르면 요약이 잘린다

성공 로그에만 색·표식을 붙여 두고 그것으로 결과를 잘라 내면,
**실패했을 때 결과가 통째로 안 보인다.** 그리고 출력 줄 수를 자르면
**맨 마지막 요약(N/N)이 먼저 잘린다** — 정작 「통과했나」를 못 읽는다.

**요약 줄은 항상 따로 한 번 더 찍는다.** 잘려도 그것만은 남게.

#### ⚠ 비동기 에디터 API 는 `-quit` 전에 안 끝난다

에디터 API 중에는 **요청만 걸고 나중에 처리되는 것**이 있다 (패키지 임포트 등).
배치모드는 메서드가 끝나면 바로 종료하므로 **그 작업이 통째로 날아간다** —
그런데 **성공 로그는 찍힌다.**

> **[사고]** 폰트 리소스 패키지를 임포트하는 배치 단계가 「임포트 요청 — <경로>」를 찍고
> 종료 코드 0으로 끝났다. **파일은 하나도 안 생겼고**, 그것을 전제로 한 다음 단계가
> `NullReferenceException` 으로 죽었다.

| 대응 | 내용 |
|---|---|
| **결과를 검사한다** | 「요청했다」가 아니라 **생겼는지 파일로 확인**한다. 그 검사를 같은 메서드 안에 넣는다 |
| 동기 경로가 있으면 그걸 쓴다 | 같은 일을 하는 동기 API 나 **직접 처리**가 있으면 그쪽이 낫다 |
| 없으면 단계를 나눈다 | 한 배치에서 요청하고 **다음 배치에서** 결과를 쓴다 |

**패키지 파일은 대개 gzip tar 다.** 안이 `<guid>/pathname` · `<guid>/asset` 구조라
**직접 풀어 쓰는 것이 가장 결정적**이다 — 비동기에 기대지 않는다.

#### ★★ 입력 판정은 **재생 안에서만** 잰다 — 편집 모드 레이캐스트는 원리적으로 빈다

「버튼이 안 눌린다」·「끌어도 안 움직인다」를 확인하려고
편집 모드에서 UI 레이캐스트를 쏘면 **아무것도 안 맞는다.**
무엇이 가로막은 것처럼 보이지만 **그런 것이 아니다** —
재생하지 않으면 캔버스가 한 번도 그려지지 않아 **모든 그래픽의 그리기 깊이가 미정으로 남고**,
레이캐스터는 그 상태의 그래픽을 **전부 건너뛴다.**

> **[사고]** 「칸이 포인터를 안 받는다」로 읽고 배치를 의심해 고쳤다.
> 진단을 찍어 보니 `raycastTarget=True · cull=False · 활성=True` 인데 **깊이만 `-1`** 이었다.
> 그래픽 장치를 띄워도(`-nographics` 를 빼도) 같았다 — **편집 모드라는 것 자체가 원인**이다.

| 대응 | 내용 |
|---|---|
| **대조군을 같이 쏜다** | 「사람이 눌러서 된다」고 아는 대상(모드 버튼 등)을 같이 쏜다. **그것까지 안 맞으면 게임이 아니라 검사 환경**이다 |
| **재생 모드 검사를 만든다** | 배치에서 재생에 들어가 **실제 포인터 이벤트**를 흘린다 (아래) |
| 진단을 같이 찍는다 | 「안 맞았다」만 찍으면 원인이 안 갈린다 — `raycastTarget` · 깊이 · `cull` · 부모 캔버스를 같이 찍는다 |

**배치모드에서 재생에 들어가는 법:**

| 단계 | 왜 |
|---|---|
| 1 | `-quit` 을 **뺀다** | 붙이면 진입 메서드가 끝나는 순간 꺼진다 — **재생은 그 뒤에 시작**되므로 영영 안 들어간다 |
| 2 | `-nographics` 도 **뺀다** | 그려야 아는 것을 재는 중이다 |
| 3 | 진입 메서드는 씬을 열고 **재생을 «요청»만** 한다 | 그 메서드 안에서 기다리면 재생이 시작되지 않는다 |
| 4 | 재생 시작 훅에서 **검사기를 심는다** | 도메인 리로드로 정적 필드가 날아가므로, **리로드를 넘는 저장소**에 표시를 남겨 두고 그것을 보고 심는다 |
| 5 | 검사기가 **스스로 끝낸다** | `-quit` 이 없으니 끝내는 것은 검사기다. **바깥에도 시간 제한을 건다** — 검사기가 터지면 배치가 영영 안 끝난다 |

⚠ **매니저를 직접 부르지 않는다.** 레이캐스트로 맞춰서 그 결과에 이벤트를 흘려야
**배선이 끊기거나 무엇이 가로막은 것이 여기서 걸린다.** 직접 부르면 「배선이 끊겨도 통과」한다.

#### ⚠ 자동 검사에서 **프레임 수로 기다리지 않는다**

화면 없는 재생은 **초당 수천 프레임**이 돈다.
「60프레임 기다렸는데 아무 일도 없다」가 실제로는 **0.01초**여서,
멀쩡히 도는 주기 로직이 **멈춘 것으로 보인다.**

> **[사고]** 0.1초 주기의 게임 루프를 「60프레임 방치」로 확인해 「틱이 안 돈다」로 읽었다.
> 시간 기준으로 바꾸니 **1.5초에 11,132프레임**이 돌았고 — 60프레임은 **0.008초**였다.

시간에 걸린 것(틱 · 타이머 · 연출)은 **시간으로 기다린다.**
기다린 뒤 **실제 경과 프레임 수를 같이 찍어** 환경 속도를 로그에 남긴다.

### ⚠ 하네스가 초기화를 대신할 때는 **게임과 같은 호출**로 한다

재생이 아니면 안 도는 초기화(첫 화면 열기 등)를 하네스가 대신해야 할 때,
**창이나 컴포넌트를 직접 만지면 안 된다.** 그러면 게임의 진입 경로가 끊겨 있어도 통과한다 —
검사가 아니라 **자기 자신을 검사하게 된다.**

> 게임 코드가 부르는 그 한 줄(화면 전환 함수 등)을 **그대로** 부른다.
> 어디를 불러야 하는지 모르면 초기화 코드의 **마지막 줄**을 본다.

### ⚠ 「영향이 없다」도 **실측으로 확증하고 등재**한다

원본에 남는 상태·죽은 값이 있으면 「어차피 안 보이니 괜찮다」로 넘기기 쉽다.
그런데 그건 **추론**이고, 추론은 회차마다 물음표로 되살아난다.

> **벡터로 등재한다** — 「이 순서로 넣으면 변화 0」이 벡터다.
> 그리고 **상태 자체는 그대로 옮긴다.** 안 보인다고 지우면 원본과 상태 기계가 갈리고,
> 나중에 원본이 바뀌었을 때 **어디가 어긋났는지 못 찾는다.**

### 컴파일·툴 실행 순서

#### ⓪ ★ 에디터가 **재생 중이면 먼저 멈춘다** — 물어보지 말고 멈춘다

재생 중에는 이식 작업이 **하나도 제대로 안 된다.**

| 증상 | 원인 |
|---|---|
| `isCompiling=True` 로 영원히 고착 | 「Recompile After Finished Playing」 설정이라 컴파일이 보류된다 |
| 새 메뉴가 안 뜬다 · 새 타입이 로드 안 된다 | 위와 같은 이유. 옛 어셈블리가 돌고 있다 |
| 프리팹을 구워도 반영이 안 된다 | 재생 중 `AssetDatabase` 쓰기는 신뢰할 수 없다 |
| 검증 하네스가 **실행 중인 게임 상태를 갈아엎는다** | 하네스는 임의 상태를 주입하는 물건이다 (「검증 하네스는 게임 상태를 갈아엎는 물건이다」) |

```
manage_editor(action="stop")     ← 작업 시작 전에 무조건 한 번
```

**멈추는 것이 파괴적 행위가 아니다.** 재생 상태는 원래 휘발이고, 디스크 세이브는
그대로 남는다. 반대로 **재생 중인 채로 진행하면** 위 넷이 조용히 섞여
「고쳤는데 안 바뀐다」를 몇 시간 뒤지게 된다.

> **[사고]** 재생 중인 걸 모르고 컴파일이 안 끝나기에 우회해서 하네스를 직접 불렀고,
> 돌아가던 게임의 세이브 객체가 230번 갈아엎혔다. 컴파일도 그동안 계속 보류 상태였다.

#### ⓪-b ★ 「에디터가 새 코드를 안 먹는다」의 **첫 번째 용의자는 컴파일 에러**다

> **[사고]** 새 필드가 로드되지 않아 웨지(아래)로 판단하고
> `ForceUpdate` · `RequestScriptCompilation(CleanBuildCache)` · `RequestScriptReload` · 파일 touch 를
> 차례로 돌리며 **여러 차례 수 분씩 기다렸다.** 실제 원인은 **에디터 어셈블리의 컴파일 에러 한 줄**이었다.
> 유니티는 컴파일이 실패하면 **직전 성공 어셈블리를 그대로 물고 있는다** —
> 그 상태가 `isCompiling=False` + 옛 DLL 로 보이고, 웨지와 **겉모습이 똑같다.**
>
> 게다가 유니티 콘솔에는 에러가 안 떴다. 유니티가 그 파일 변경을 아직 집어가지 않았기 때문이다.
> **`dotnet build` 한 번이면 즉시 나왔다.**

**순서를 고정한다.**

```bash
dotnet build Assembly-CSharp.csproj -nologo -v q          # ← 항상 여기부터 (프로젝트의 런타임 csproj)
dotnet build Assembly-CSharp-Editor.csproj -nologo -v q   #    (프로젝트의 에디터 csproj)
```

**0 에러를 확인하기 전에는 에디터를 의심하지 않는다.** 판별식:

| 관찰 | 뜻 |
|---|---|
| `dotnet build` 에러 있음 | **컴파일 에러**다. 웨지가 아니다 |
| `dotnet build` 0 에러 + 옛 DLL + `isCompiling=False` | 진짜 웨지 — 에디터 창 클릭이 필요하다 |
| `isCompiling=True` 로 고착 | 재생 중이거나(ⓞ) 포커스 대기 |

**`dotnet build` 0 에러는 「파일이 맞다」는 증명이지 「에디터가 새 어셈블리를 물었다」는 증명이 아니다.**
재생·측정에 들어가기 전에 로드된 어셈블리에 **새 멤버가 존재하는지 리플렉션으로 찍어** 확인해야 증명된다.

- **컴파일 검증은 에디터를 기다리지 말고 바로 돌린다** — 위 「순서를 고정한다」의 명령과 동일하다
  (프로젝트는 한 번에 하나만 지정).
- 에디터 툴 실행은 `새로고침 → **컴파일 완료 확인** → 메뉴 실행 → 콘솔 확인`.
  **컴파일 전에 메뉴를 돌리면 옛 어셈블리가 실행돼 파일이 안 바뀐다.**
- ⚠ **wedge 증상** — `isCompiling=True` 로 고착되고 어셈블리가 리로드되지 않는다.
  유니티가 **포커스를 기다리는 중**이다. `AssetDatabase.Refresh` + `RequestScriptCompilation`
  을 직접 불러도 안 풀린다. **에디터 창을 한 번 클릭해야 한다.**
  판별법: 에디터에서 읽은 상수 배열 길이가 소스와 다르면 옛 어셈블리다.
  ```csharp
  return Generator.Ratios.Length;   // 소스는 7인데 5가 나오면 리로드 안 된 것
  ```
  급하면 **같은 수식으로 산출물을 외부(파이썬 등)에서 굽고**, 나중에 에디터 툴로 재생성한다.
- **에셋을 코드로 만들 때 `AddObjectToAsset` 은 재임포트를 유발한다.** 그 시점의 디스크 상태로
  메모리 내용이 되돌아가 **앞서 채운 리스트가 통째로 날아간다.**
  → 서브에셋을 **먼저** 붙여 저장하고, 그다음 데이터를 채운 뒤
  `SetDirty` + **`SaveAssetIfDirty(asset)`** 로 확정한다.
- 아이콘 생성기가 조용히 죽을 수 있다 — 텍스처가 메모리 매핑 중이면 IO 예외 후
  **그 뒤 전부가 안 구워진다.** 내용 같으면 건너뛰고, 실패하면 재시도하고, 그래도 안 되면 경고.
- ⚠ **빌드 중 NRE 를 「원래 뜨는 것」으로 넘기지 마라.** 굽는 코드가 `AddComponent` 뒤에 참조를
  주입하면 굽는 시점의 `Awake` 가 null 을 만진다. 방치하면 **「경고 0」을 완료 기준으로 못 쓴다** —
  진짜 결함이 그 노이즈에 묻힌다. `Awake` 쪽에 null 가드를 넣어 0으로 만든다.

### 점수를 믿기 전에

- **캡처 쪽이 원본 아트와 다를 수 있다.** 헤드리스 캡처의 색 프로파일 때문에 캡처가 원본 PNG보다
  밝게 나오는 경우가 있다. 점수가 낮으면 **원본 에셋과 직접 대조**해 본다.
- **기준 캡처가 「렌더 전 상태」일 수 있다.** 캡처를 그대로 베끼면 조작 불가능한 빈 칸이 남는다 —
  **원본 코드가 실제로 그리는 것**을 만들고 캡처가 비워둔 자리에 끼워 넣는다.
- ★ **캡처에서 「읽어낸」 것을 사양으로 삼지 마라. 판정은 항상 ①원본 코드 → ②규약 문서 → ③캡처다.**
  > **[사고]** 모집 확률표 셀이 캡처만 보면 `LR · LEGEND RARE` 두 줄 같았다.
  > DOM 을 열어 보니 **`LR` 한 덩어리**였다. 캡처를 베꼈으면 원본에 없는 요소가 생겼을 것이다.

  **글자·숫자·라벨은 반드시 DOM/JS 문자열에서 확인한다.** 픽셀로 읽으면 커닝·글로우·인접 요소가
  붙어 없는 것이 보인다.
- **직관과 반대인 값이 나와도 원본과 같으면 맞다.** 강화를 받는데 사거리가 줄어드는 것처럼
  이상해 보이는 결과가 원본 계산식의 정답일 수 있다. 「이상하다」로 고치지 말고 **원본에서 같은
  상태를 만들어 같은 값이 나오는지 확인**한 뒤 판단한다.

## 원본 코드에서 답 찾는 법

**[예시]** — 함수명·CSS 클래스명은 원본마다 다르다. 모양만 베끼고 이름은 그 원본의 것으로 갈아끼운다:

```bash
# 화면/함수 찾기
grep -n "function drawBay\|function drawSpaceWindow" 원본.html
# CSS 규칙
grep -n "^\.collect-chip\|^\.stat{" 원본.html
# 화면이 부르는 draw 트리를 재귀적으로 끝까지 편다
grep -n "function drawBay" -A 12 원본.html
# 그리기 파라미터를 전수로 뽑는다 (연출 필수)
grep -n "lineWidth\|shadowBlur\|globalAlpha\|globalCompositeOperation" 원본.html
# 메인 루프의 게이트 조건 (클라 필수)
grep -n "_loopBody\|requestAnimationFrame" -A 6 원본.html
```

### ⚠ 문서의 라인 번호를 믿지 마라

기획서·플레이북의 라인 번호는 **작성 시점 빌드 기준**이라 현재와 어긋난다.
**오프셋은 구간마다 다르다** — 원본이 100줄 늘었다고 전 구간이 +100 이 아니다.
앞 구간은 +7, 뒤 구간은 +103 인 식이라 **일괄 보정이 통하지 않는다. 항상 grep 으로 확정한다.**

### 실측 지도 — **학습 단계에서 그 프로젝트의 것으로 만든다**

원본이 한 파일에 수천 줄이면 매번 처음부터 찾게 된다. **구간 → 담당** 표를 한 번 만들어 두고
인용할 때마다 갱신한다. 이 표는 그 프로젝트의 원장에 산다 — **여기에 특정 원본의 라인을 적지 않는다.**

| 채워야 하는 구간 | 무엇을 적나 |
|---|---|
| CSS 전량 | 시작~끝 라인 · 규칙 수. UI/UX 가 여기서 치수를 캔다 |
| DOM 구조 | screen 단위 · 오버레이(팝업) 목록. 화면 수의 분모가 여기서 나온다 |
| 모듈 계약 | 원본이 전역으로 노출하는 객체 — 우리 쪽 인터페이스 경계가 된다 |
| **스탯 계산 본체** | 파생 스탯이 나오는 함수. 수치 환원의 중심이라 ★ 로 표시한다 |
| 단계·누적 보정 | 스테이지/방치/메타 보정 함수 — 계산 순서가 결과를 가른다 |
| draw 계열 | 유닛·적·발사체 그리기 함수. 연출 파트의 진입점 |
| 스프라이트 캐시 | 원본이 미리 굽는 자리. 여기 있는 것은 우리도 구워야 한다 |
| 생성 · 피격 · 사망 | 전투 상태 전이 3점 |
| 상한·공간분할 상수 | 개체 수 캡·셀 크기 — A/B 개체 수 판정의 기준 |
| **메인 루프** | `dt` 클램프 · **정지 게이트 조건**. 한 줄씩 옮긴다 |
| 합성 정책 | 캔버스 `globalCompositeOperation` 이 바뀌는 지점 전부 |
| 화면 전환 · 재화 갱신 | 플로우 diff 의 기준점 |
| 표기 테이블 | 수치를 문자열로 바꾸는 규칙 — 파생 표기가 여기 산다 |
| 치트·디버그 훅 | **A/B 상태 맞추기용.** 있으면 측정 비용이 크게 준다 |
| 저장 스키마 | 세이브 구조의 원본. 상태 주입의 계약 |

> **주의** — 원본의 id·변수명이 화면 이름과 어긋나 있는 경우가 흔하다
> (예: `#hangar` 가 실제로는 다른 화면). **이름이 아니라 그리는 내용으로 판정하고**,
> 어긋난 쌍을 발견하면 그 자리에서 지도에 적어 둔다.
